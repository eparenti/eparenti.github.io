verified-dispatch
In design
Go · one static binary · code starts next

For people who run coding agents from an orchestrating agent

Dispatch a builder. Verify its work from git facts. Read a short receipt.

verified-dispatch runs a builder agent as a subprocess on one slice of a plan, watches it for stalls, and when it ends checks what the builder claims against what git shows. The orchestrator never reads the builder's transcript. It reads a receipt of at most 40 lines, and a receipt that says VERIFIED can be acted on without reading anything else.

The command is vdispatch. It works in any git repository on Linux or macOS with any builder that runs without a terminal: Claude Code, Codex, a Cursor command, or a script. It never calls a model and never opens a network connection.

The transcript stays out of the orchestrator

Builder output, diffs, and gate logs are the largest part of a long orchestrating session's context. They go to files on disk. The session gets the receipt.

Every check runs mechanically, every time

Reported hashes against the log, history intact, refs intact, tree clean, gate rerun: rules an orchestrator applies by hand today, run by code with the same result each time.

Stalls end without a watcher

No new commit for a configured time, or a wall-clock limit, or an output cap, ends the run. Nothing the builder started survives it.

Where it sits between the orchestrator and the builder

What it does not do. It does not summarize with a model, judge code quality, retry, or schedule several builders. It reports what happened; the orchestrator decides what to do next. It does not protect against a builder with root or with write access to the tool's own binary and state directory, and its docs say so.

From a builder's claims to a verified receipt

A builder says it is done and lists two commits. One hash is not in the run, and a third commit was made but not claimed. The receipt says UNVERIFIED and names each fact. The orchestrator reads twelve lines and knows exactly what to check.

Example: a receipt with findings

Designed output
vdispatch run 20261106T184200Z-7f3a2c   repo ~/work/thing   branch feat/map-default
slice    task3.md   builder claude-code   22m 14s   builder exit 0
status   UNVERIFIED   integrity ok   (1 claim unresolved, 1 unclaimed, gate pass)

commits  2 new on baseline 815a73e
  6cacea9  "feat(map): default -m to config"        claimed, verified
  91be02d  "test(map): cover the warning once"      unclaimed
  a1b2c3d                                            claim unresolved

checks   tree clean, history intact, refs intact, git state intact
gate     PASS   exit 0   41s   "make check"
files    4 changed, +212 -18
logs     vdispatch log 20261106T184200Z-7f3a2c

The JSON receipt beside the text is the authority. Status and check lines come only from the tool; a builder cannot print a line that looks like one.

VERIFIED, exit 0

The builder reported done, made at least one commit, every check passed, the gate passed, and the starting tree was clean. Act on it without reading anything else.

Anything else, exit 1 to 8

UNVERIFIED, GATE-FAILED, BLOCKED, FAILED, NO-RESULT, STALLED, REFUSED, or ERROR. The receipt names the failing check or the reason, and the integrity flag is reported on its own so a stall cannot hide a rewritten history.

Why a dirty tree is refused

A run starts only from a clean tree. With --allow-dirty it still runs, records a content hash per dirty path, and checks that no dirty work was lost or committed by the builder. A run started that way can never be VERIFIED.

How a repository adopts it

Two files and no daemon. The home config holds builder presets and secret patterns. A file at the repository root names the gate and the preset.

  1. Name the gate and the builder.

    A .vdispatch.toml at the repository root names the gate command and a builder preset. The gate runs under bash with the same trust as running the repository's own tests.

  2. Dispatch a slice.

    vdispatch run --slice task.md. The slice is the plan text; the tool appends a fixed contract that tells the builder how to report. Hosts that cap foreground commands use --detach and vdispatch wait.

  3. Read the receipt.

    Forty lines at most. Scripts read the exit code and the integrity flag. vdispatch log opens the raw streams when someone wants them, redacted by default.

.vdispatch.toml

gate = "make check"
builder = "claude-code"
commit_stall_minutes = 20

Dispatch

vdispatch run --slice task.md
vdispatch run --slice task.md --detach   # prints the run id
vdispatch wait <run-id> --timeout 90
vdispatch check                          # the checks and the gate, no builder

Presets for Claude Code and Codex ship in the binary. Repositories may lower the stall timeout and never raise it above the cap.

Statuses and exit codes
StatusMeaningExit
VERIFIEDDone, at least one commit, every check and the gate pass, clean start0
ERRORThe tool failed or the run was aborted1
UNVERIFIEDA check failed, or the run used --allow-dirty2
GATE-FAILEDGate exit nonzero, timeout, or output cap3
BLOCKED / FAILEDThe builder reported it could not finish4 / 5
NO-RESULT / STALLED / REFUSEDNo valid result file; a stall or cap fired; refused before the builder ran6 / 7 / 8

Linux has full containment: a new session, a child subreaper, and a death signal for the builder. On macOS the receipt says containment: process group only.

How to follow it

The repository is public from the first commit. Watch it for the first release, then dispatch one slice of your own plan and compare the receipt with what you would have read by hand.
