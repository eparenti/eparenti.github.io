For people whose lead coding agent hands work to builder agents

Hand work to a builder agent and verify what it did.

verified-dispatch is a command line tool, vdispatch, for a lead coding agent that hands parts of a plan to a builder agent. As designed, it runs the builder, stops it if it stalls, checks the builder's claims against git, runs the project's tests itself, and returns a receipt of at most 40 lines. Today the merged code is the command shell and the layer that runs git; the rest is designed and being built.

The problem. When a lead AI agent hands work to a builder agent, it cannot trust the report it gets back. To check, it reads the builder's transcript and diffs, which fills its own context and costs money, and then checks commit hashes and the working tree by hand. A builder that stalls keeps running until someone notices.

As designed, you get one program for Linux and macOS with no runtime dependencies. It works in any git repository, with any builder that runs without a terminal, such as Claude Code, Codex, or a script. It never calls a model and never opens a network connection.

The lead agent reads a short receipt

Builder output, diffs, and test logs go to files on disk. The lead agent gets a receipt of at most 40 lines, and a receipt that says VERIFIED can be acted on without reading anything else.

The same checks every time

Claimed commits, history, branches, a clean working tree, and the test run are checked by code, from git facts. These are rules a person or a lead agent applies by hand today, and sometimes forgets.

A stalled builder is stopped

No new commit for 20 minutes by default, a total time limit, or an output limit ends the run. Then every process the builder started is stopped.

How a hand-off is designed to work

What it does not do. It does not summarize with a model, judge code quality, retry, or run several builders from one command. It reports what happened, and the lead agent decides what to do next. It does not sandbox the builder (lock it in a restricted environment): the builder runs as the same user, with that user's permissions. The tool detects the changes it can see in git and in its own files, and its design lists what it cannot see.

From a builder's claims to a receipt

A builder says it is done and lists two commits. One hash is not in the run, and a third commit was made but not claimed. The designed receipt says UNVERIFIED and names each fact, so the lead agent knows what to look at.

Example: a receipt with findings

Designed format (planned)
vdispatch run 20261106T184200Z-7f3a2c   repo ~/work/thing   branch "feat/map-default"
slice    "task3.md"   22m 14s   builder exit 0
status   UNVERIFIED   integrity ok   (1 claim unresolved, 1 unclaimed, gate pass)

commits  2 new on baseline 815a73e
  6cacea9  "feat(map): default -m to config"     claimed, verified
  91be02d  "test(map): cover the warning once"   unclaimed
  a1b2c3d                                         claim unresolved

checks   git state intact, history intact, refs intact, tree clean, nothing staged
gate     PASS   exit 0   41s   gated 91be02d
files    4 changed, +212 -18
summary  "Added the map default and its tests."
logs     vdispatch log 20261106T184200Z-7f3a2c

The gate is the project's test command. A JSON receipt next to the text is the record that counts. Status and check lines come only from the tool, so a builder cannot print a line that looks like one.

VERIFIED, exit 0

The builder reported done and made at least one commit, every check passed, the project's tests passed in a separate clean copy, and the run started from a clean tree. Act on it without reading anything else.

Anything else, exit 1 to 8

UNVERIFIED, GATE-FAILED, BLOCKED, FAILED, NO-RESULT, STALLED, REFUSED, or ERROR. The receipt names the failing check or the reason, and scripts read the integrity flag as well as the status.

Tests run in a separate copy

As designed, the project's test command runs in a separate git worktree (a second checkout of the same repository) that the builder does not work in. Only a run tested there can be VERIFIED. A run that starts from a tree with uncommitted changes is refused unless --allow-dirty is given, and such a run can never be VERIFIED.

Status stated. The design is complete. The merged code is the vdispatch command shell, where only vdispatch version works and every other command reports that it is not implemented yet, and the layer that runs git with fixed settings. Configuration is in an open pull request. Everything else on these pages, including the receipt above, is the design.

What exists today, and what is planned

The repository is public. The steps below show how a repository is designed to adopt the tool. The table shows each major part and its state today.

  1. Name the test command and the builder.

    A .vdispatch.toml file at the repository root names the test command and a builder preset (a named, ready-made builder command). The tool reads it from the last commit, never from disk, so a change to it always shows up as a commit. Reading this file is in the open pull request.

  2. Hand over one part of the plan.

    vdispatch run --slice task.md runs the builder on that file and adds fixed instructions on how to report. Agent hosts that stop long commands can use --detach and vdispatch wait. Planned.

  3. Read the receipt.

    Forty lines at most. Scripts read the exit code and the integrity flag. vdispatch log shows the stored output, with secrets removed, when someone needs it. Planned.

.vdispatch.toml (open pull request)

[gate]
command = "make check"

[builder]
preset = "claude-code"

[limits]
commit_stall_minutes = 20

Commands

vdispatch version                        # works today
vdispatch run --slice task.md            # planned
vdispatch run --slice task.md --detach   # planned
vdispatch wait <run-id> --timeout 90     # planned
vdispatch check                          # planned

Presets for Claude Code and Codex are built into the program, in the open pull request. A repository may lower the stall time and the other limits but never raise them above the built-in caps. It may name a preset, but it may never supply its own builder command.

As designed, Linux gets the fullest control over the builder's processes. On macOS the tool looks for leftover processes once a second, and the receipt says that control there is weaker.

How to follow it

Watch the repository for the first release. Then hand one part of your own plan to a builder through it, and compare the receipt with what you would have read by hand.
