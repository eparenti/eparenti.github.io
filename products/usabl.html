usabl
Early release · Apache-2.0
v0.2.2 · build from source

For teams that build web apps, by hand or with an AI coding assistant

Find accessibility barriers in a code change and fix them before it ships.

usabl checks the screens a code change touches, in a real browser, and tells you whether the change added an accessibility barrier (something that stops a person with a disability from using the screen, such as a button a screen reader cannot name). It works the same whether you wrote the code by hand or an AI assistant wrote it. Its fix command has your AI coding assistant repair each accessibility barrier in the source code and check again.

The problem. Accessibility is often checked late, if at all. The check usually comes from a separate audit near release, outside daily development work, so a team under deadline can skip it. By the time anyone looks, the accessibility barriers have already reached users and cost more to fix.

You get one command line tool, and the same checks in the places you already work: an overlay in your dev server, a hook that runs when your coding assistant tries to finish, a pull request check in GitHub Actions, and a helper for tests written with Playwright (a browser testing tool). A fix skill has the assistant repair each accessibility barrier in the source code and check again.

Turn it on without fixing old problems first

usabl records the accessibility barriers already in your app. Only a new one blocks a change, so a team can start using it today.

The same result every time

Results come from fixed rules run in a real Chromium browser: axe-core (a widely used open-source rule engine), a PatternFly rulepack (extra rules for apps built with that design system), and a keyboard walk (a test that moves through the screen with the Tab key). usabl calls no AI model. An assistant can fix a problem, but it cannot decide the result.

A result you can check later

A verified run writes a receipt tied to the exact source tree, the rules, and the engine and scanner versions. A change to any of them makes the receipt stop matching.

How a change gets a verdict

What "verified" means. On the screens usabl checked, the change added no new accessibility barrier that a machine can detect, compared with the ones already recorded. A run that checked nothing, or could not finish, returns no verdict, and that never counts as a pass. Verified does not mean the app is accessible or meets a legal standard.

From a changed component to a verdict

A dialog that no longer keeps keyboard focus inside it looks fine in a visual review, but a keyboard user's focus moves to the page behind it. usabl sees which screen the change touches, scans that screen, and blocks the change.

Example: set up, then check a change

Real commands
npx usabl init       # draft the config and the route map from your code
npx usabl baseline   # record the accessibility barriers already there
npx usabl brief      # before a task: screens it reaches, checks, what done means
npx usabl check      # after the change: one verdict
npx usabl debt       # what remains, by screen and rule, and how old it is

The route map says which files render which screens. usabl brief and usabl debt are on the main branch and are not in a release yet.

Verified, exit code 0

Every touched screen opened and was scanned, and nothing new appeared beyond the record. A receipt records the source tree, the rules, and the versions.

Anything else blocks the change

Regression exits 1, approval required exits 2, and not covered exits 3. A screen usabl could not check is reported as a gap, never guessed. The pull request check fails. The assistant hook sends the assistant back once; if it stops again, the stop is allowed and marked NOT verified.

New on the main branch since v0.2.2

usabl brief tells an assistant, before it starts a task, which screens the task's files reach, which checks apply to each, and what counts as done. It opens no browser and gives no verdict.

Voice requirements let a team write what a screen reader user must hear after each step, such as a message after a delete. A live scan runs them with a simulated screen reader. Their findings are shown as preview and do not change the verdict until the team promotes that kind of check.

The pull request check can also keep a history of the main branch. When two scans confirm a fix, its place in the record closes, so a new accessibility barrier cannot take it. usabl debt shows what remains and how old it is.

Keep expert judgment with your team. WCAG 2.2 is the main international standard for web accessibility. usabl checks 21 of its 55 Level A and AA success criteria by machine. It does not claim compliance, replace expert audits or testing with people who use assistive technology, or judge whether alternative text is useful.

Try it on one app

usabl needs Node.js 22 or later. It is not on npm yet, so you build it from source in a folder next to your app, then draft its files from your code.

  1. Build the release.

    Clone the v0.2.2 tag, build it, install Chromium for Playwright, and add usabl to your app as a local dependency. The newer commands are on the main branch, which can change at any time.

  2. Draft, review, commit.

    usabl init drafts the configuration and the route map from your code. usabl baseline scans every mapped screen to record the accessibility barriers already there. Commit each file before the next step, because usabl does not trust rule files with uncommitted changes.

  3. Add the places you work.

    One command each adds the dev-server overlay, the Claude Code hook and skills, the Cursor hook, and the GitHub Actions check. usabl doctor reports what is set up and what is missing.

Build and link

git clone --branch v0.2.2 https://github.com/usabl-dev/usabl.git
cd usabl && npm ci && npm run build
npx playwright install chromium
cd ../your-app && npm install --save-dev file:../usabl

First run

npx usabl init
npx usabl baseline
npx usabl check
npx usabl install --claude-skill
npx usabl install --ci

In CI (the automated checks that run on each pull request), the pull request is built in a job with no secrets and judged in a separate job. So the app must build to static files, and appBaseUrl in the config must be a loopback address (one on the same machine) with a port, such as http://127.0.0.1:5173.

Route discovery is built for React apps. The overlay supports Vite, and webpack on main; rspack and Next.js are not supported yet. Screens behind a sign-in need a saved session. usabl has not been tested against a large number of apps at once.

A good first test

Point usabl at one React app with a known accessibility barrier, or at the usabl-app sample, a PatternFly 6 app with known accessibility barriers. Record what is there, break a dialog's keyboard focus, watch the check block, fix it, and read the receipt with the people who approve accessibility work.
