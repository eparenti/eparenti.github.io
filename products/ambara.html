For developers and teams who use AI coding agents

Give AI coding agents project memory that lasts between sessions.

Ambara gives AI coding agents shared project memory that lasts between sessions. Handoffs, decisions, and status are kept as plain Markdown files in a git repository. At the start of each session, the agent reads what applies to its project before it touches code.

The problem. AI coding agents forget everything between sessions. People explain the same decisions again and again, and notes kept inside one agent tool do not reach teammates who use another.

You get a command line tool, an MCP server (MCP is the standard way coding assistants connect to outside tools), and a git repository of Markdown files that holds the context. You talk to your agent as usual. Say "save where I left off" or "record that decision" and Ambara files it.

The next session starts where the last one stopped

At the start of a session, the agent asks Ambara for context. It gets the open handoffs, team decisions, and project status that match its project, in a short summary.

Team decisions are reviewed and shared

A decision is proposed on a review branch, and the team reviews it like code before it counts. Because the context is plain files in git, every agent tool and every person can read the same history.

Nothing is kept that you did not ask to save

Ambara stores only what someone asks it to save. Text that looks like a password or key is blocked before any save. It keeps no log of what agents read and does not track who is online.

Where Ambara sits between your agents and your team's context

What "saved" means. A handoff is written at once to a short-lived branch and expires on its own, after 72 hours by default. A status update opens a light review request. A decision or workflow is proposed on a review branch for the team to review. If Ambara could create only the branch and could not open a review request, it says so.

From "what did we decide?" to an answer with a source

A new session is asked about the auth migration. The agent reads the decision the team recorded, with its date, status, and the projects it applies to, and answers from that.

Example: a saved decision

Real entry format
---
type: decision
title: Use gRPC for internal services
status: active
projects: [api-platform]
created: 2026-01-15T10:00:00Z
---

REST endpoints between auth and billing are creating versioning friction.
Use gRPC for all new internal service communication. REST stays for public APIs.

Each entry is one Markdown file. The block between the --- lines holds labeled fields. The five types are active (a handoff that expires), project (current status), decision, workflow (a team process), and principle (a lasting standard).

The next agent starts informed

At session start the agent gets the handoffs, decisions, and status that match the project in a short summary. It reads the full text of an entry only when it relies on it.

A save is blocked or only partly done

Text that looks like a password or key is blocked before it is saved, and Ambara says why. Personal or confidential terms that a team configures send the entry to review. If only a branch exists, Ambara says that no review request was opened.

Pull requests and issues as context

Ambara can also read labeled GitHub pull requests, GitLab merge requests, and Jira issues and show them to the agent as project context, for example work to continue or a handoff to pick up. Unlabeled items are ignored. Linear and Confluence work only with sample data so far. Ambara does not call their live services yet.

In CI (the automated checks that run on each change), a commit message whose first line starts with ambara: can file an entry. It passes the same content checks as a save from the agent.

What Ambara does not do. It is not a secrets manager, a monitoring product, an agent runtime, or a meter of total model cost. It does not record who read what or who is online, and it does not skip git review. Support for a specific agent tool is claimed only after that tool has been checked.

Try the offline demo, then connect a project

The demo builds a sample context repository, a connected project, sample pull request data, and a proof script that runs with no network. Then one command connects a real project.

  1. Install from the repository.

    Ambara needs Python 3.12 or newer. Install it from GitHub with pipx (a tool that installs Python command line programs).

  2. Run the demo.

    ambara demo creates an ambara-demo folder. Its run-proof.sh script checks startup, reads, saves, review branches, commit capture, and the count of text kept out, all on your computer.

  3. Connect a project.

    In a project folder, ambara onboard --yes creates a local context repository, adds agent instructions to CLAUDE.md, sets up the MCP server, and turns on handoffs. Restart the agent. For a team, run ambara onboard --remote <git-remote-url> with one shared repository on GitHub or GitLab.

Install and try the demo

pipx install git+https://github.com/ostinato-forge/ambara.git
ambara demo
cd ambara-demo
./run-proof.sh

Connect a project

cd your-project
ambara onboard --yes
ambara doctor --check-startup

ambara startup writes the context to a plain file for agents that cannot use MCP. ambara html builds static web pages of the context so a person can read it directly. ambara value shows the running estimate of text kept out of sessions.

A good first test

Run the demo proof. Then connect one project you work on with two agents. Save a handoff at the end of one session and check that the next session starts from it. Then propose one decision and review the branch it creates.
