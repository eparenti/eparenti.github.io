Product Lab
Research prototype · Apache-2.0
Version 0.1.0 · demo on simulated data

For people who shape a product with an AI assistant

Develop a product around its audience, from a loose idea to tested alternatives.

Product Lab helps you and your AI assistant develop a product for a defined audience. Starting from a loose idea, the assistant drafts who the product is for: the people, their path through the product, and the outcomes they want. It builds distinct alternatives and reviews the whole experience. A local engine then tests the alternatives with experiments and checks whether each lesson also helps on later work.

The problem. An AI assistant can build many versions of a product quickly. Building them does not say who the product is for, what better means for those people, or which version serves them. Product decisions end up settled by opinion, and a lesson from one round is rarely checked on the next piece of work.

You get a skill (an instruction file that tells the assistant how to do this work), with plugin files for Claude Code and Codex, and a command line engine in plain Python with no outside packages. The bundled demo runs from a fresh copy of the repository with no model, GPU, network access, or install step.

Every measure points to a real user need

The assistant first drafts who the product is for: their situation, their path through the product, and the outcomes they want. The engine refuses a measure that does not point to one of those outcomes.

The pass rule is fixed before the run

Before any version runs, you state the main measure and its minimum gain, and how far each other measure may fall. A better score cannot make up for a failed required check.

Lessons are tested on work they have not seen

Some tasks are held back. A lesson is tested once on those reserved tasks, and the engine will not reuse them in that study, even after a failed run.

How a study moves through Product Lab

What a supported lesson means. A supported lesson passed its one test on reserved tasks in one recorded study. It applies to that study only. The ranges in the report show the spread over repeated runs of the same version and task. They are not statistical confidence intervals.

From a product brief to a tested lesson

The bundled demo is a simulated tool that helps an operator recover a failed job. It shows the whole loop on invented data. It does not show that any real product got better.

Example: the three demo commands

Real commands
python3 lab.py brief --product PRODUCT.json
python3 lab.py demo --output generated/first-demo
python3 lab.py report --lab generated/first-demo/study

brief prints who the product is for and what a better result means. demo runs the simulation. report shows each run, its result, and the reasons. Use a new output folder for each demo run: the engine will not overwrite earlier evidence.

A lesson is supported

On the reserved tasks it beat the current version by at least the declared minimum, every required check passed, and no other measure fell by more than its allowed loss. The report shows the range over repeated runs.

A lesson is rejected or uncertain

A failed check rejects it, whatever the scores. A missing check, or a range that overlaps the allowed loss, leaves it uncertain. Failed and incomplete runs stay in the record as failed and never become a starting point.

Use it through your assistant

Ask the assistant to read and use skills/product-lab/SKILL.md for your idea. The skill drafts who the product is for from what you already have, and asks only about choices that change the product. It labels guesses about users as guesses and never invents interviews or quotes. Plugin files for Claude Code and Codex are included. Neither has had a real trial yet.

Limits. The evaluator is trusted code that runs with your permissions. The engine is not a sandbox (a locked-down space for untrusted code). The fingerprints catch ordinary edits. They do not stop a harmful program that runs with the same permissions. Model costs, authoring time, and the cost of failed calls are not fully counted yet. Real user value, accessibility, security, and craft need evidence from the real product and real people.

Run the demo, then bring a product

Everything runs from a copy of the repository with Python 3.11 or later. There is nothing to install.

  1. Run the demo.

    brief, demo, and report show the whole loop on the simulated recovery tool.

  2. Describe your product.

    Start from PRODUCT.md and PRODUCT.json, or let the assistant draft them from your notes. You review what they mean.

  3. Write an evaluator and run a study.

    init fixes the rules and the evaluator, register copies a version, run measures it, lesson records a lesson, and validate tests it once on the reserved tasks. The evaluator and command guide covers each step.

Demo

git clone https://github.com/product-lab-ai/productlab.git
cd productlab
python3 lab.py demo --output generated/first-demo
python3 lab.py report --lab generated/first-demo/study

Checks

python3 -m unittest discover -s tests -v
ruff check .

To try the skill in Claude Code, start it from your own project folder with claude --plugin-dir /absolute/path/to/productlab, then ask it to use Product Lab on an idea. Ruff (a code style checker) is optional and only needed for development.

Product Lab is a research prototype. Its central claim, that kept lessons improve later work enough to pay for the experiments, is still untested. The repository describes a first field trial that would compare the strongest existing workflow, Product Lab with learning turned off, and Product Lab with kept lessons, on new briefs with representative users.

A good first test

Run the demo and read the report with someone who makes product decisions. Then pick one real decision your team argues about, write down who it serves, and run two versions with one evaluator you trust.
