For teams that merge agent-authored pull requests

A merge gate you can prove.

A green check says a check with the right name reported success. Siglum recomputes the verdict from the evidence, binds it to the exact commit, runs outside the pull request's control, and seals the result as a signed attestation.

Keep the validators you already run. Siglum decides whether their evidence is trustworthy enough to merge and leaves a signed record of that decision, in your organization's CI, with no hosted service.

The verdict is recomputed

Siglum takes the evidence (which validators ran, their status, their artifacts) and computes PASS, FAIL, or ERROR with explicit coverage. Anything missing fails closed.

The author is kept away from the gate

An untrusted gather job runs over the pull request and produces evidence only. A trusted job, pinned to the base branch, recomputes, signs, and posts the check.

Anyone can verify offline

The result is an in-toto attestation, keyless-signed through Sigstore and recorded in a transparency log. cosign verifies it with a strict identity policy and no Siglum service in the loop.

Where Siglum fits in your pull request

A precise meaning for PASS. A defined set of validators ran to completion over this exact commit, under a policy fixed and independent of the author for the duration of the assessment, and the recorded verdict is a pure function of that evidence. Siglum does not claim the code is safe, the tests are meaningful, or the dependencies are sound.

From a hollow green check to a sealed verdict

A contributor who can push a branch and edit CI can make a required check pass without doing the validation it stands for. Nothing is forged: the check goes green for real. Siglum closes that hole.

Example: audit a repository you can read

Real command, illustrative lines
siglum audit --repo owner/name

PR_EDITABLE_WORKFLOW  .github/workflows/ci.yml can be changed by the pull request it checks
UNRESTRICTED_CHECK    required check "ci" can be posted by any token
exit 1

The audit reads branch protection, rulesets, and workflow configuration and reports where the gate can be bypassed today. It only reads; it changes nothing. Exit 0 means no findings, 1 means findings, 2 means the audit could not complete.

PASS: mergeable, with a signed record

Every required validator ran to completion, coverage is FULL, the gate's identity and enforcement checks held, and the attestation signed and self-verified. The check turns green only after that.

FAIL or ERROR: the gate refuses

A skipped validator, an unreadable policy, a head edit to an anchored file, an approval left behind by a force-push, or a signing failure all fail closed, and the explanation comment says exactly why.

Two tiers, one core

Dry-run runs in your normal CI and previews the verdict. Use it to author policy and to see where a gate silently skips. It has no verified identity and does not sign.

Sealed is the security guarantee. It runs in an org-controlled workflow outside the pull request's pipeline, verifies its own GitHub Actions OIDC identity, and signs the attestation. It defends against a contributor who can push and edit CI but has no organization-admin rights.

Stated boundary. Siglum does not defend against a compromised organization administrator, and this version ships only read-only validators. Signing is pinned to Sigstore staging and refuses production until that path is reviewed, so every attestation is non-production today. Gating releases is a separate, opt-in step from gating merges.

Deploy the Sealed gate in your organization

Install the Python package, audit your repositories, then register your own GitHub App and pin the trusted workflow to a ref contributors cannot edit.

  1. Install and audit.

    Python 3.12 or newer. pip install -e . gives you the core and the CLI; the sigstore and github-app extras add signing and App authentication. Run siglum audit against the repositories you care about.

  2. Register your own App.

    There is no hosted Siglum service and no marketplace App. The App and its key are yours. The workflow needs the App id, installation id, and private key as secrets so it can post the check-run and the explanation comment.

  3. Pin and require.

    Deploy the org-controlled seal and enforce reusable workflow, pinned to an immutable ref, make the siglum check required in your ruleset, and restrict its source to the App. siglum setup check verifies the deployment before you rely on it.

Install

git clone https://github.com/siglum-dev/siglum && cd siglum
python -m pip install -e ".[dev]"

Walk the flow with no GitHub access

siglum demo scaffold --out /tmp/gate-proof-demo --repo owner/gate-proof-demo --force
cd /tmp/gate-proof-demo
siglum audit --config siglum-audit-config.json || true
siglum setup check --local .

The fixture audit finds PR_EDITABLE_WORKFLOW by design and exits 1. The setup check shows what a ready Sealed install looks like.

Siglum grew out of an earlier in-CI evidence check for agent-assisted pull requests. That check ran inside the pull request's own workflow, which is the hole Siglum closes.

A focused first evaluation

Run siglum audit on three repositories you merge into every week and read the findings with the people who own branch protection. Then scaffold the demo and walk the Sealed flow locally before registering an App.
