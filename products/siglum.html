siglum
Open source · Apache-2.0
v0.1 · early stage, test signing only

For teams that merge pull requests when the required checks are green

Confirm a pull request really passed its checks before it merges.

Siglum decides whether a pull request may merge by recomputing the result from the evidence its checks produced. It does this in a job the pull request cannot change, ties the result to the exact commit, and signs it. Anyone can verify the signed record later, offline, with standard open-source tools.

The problem. Teams merge a pull request when its required checks are green, but a green check means only that a check with the right name reported success. The pull request being checked can often change that check, so it can pass without doing the work it stands for, and nothing records why the merge was allowed. The gap grows as AI agents open more pull requests than people can read line by line.

You get a merge gate that runs in your own GitHub organization (two GitHub Actions workflows and a GitHub App that you register), a read-only audit that shows where your current checks can be bypassed, and a signed record of every decision. There is no hosted service.

The result comes from the evidence

Siglum reads what each check reported and computes the result itself: PASS, FAIL, or ERROR, plus whether every required check gave a definite answer. A missing or skipped check blocks the merge. This is called failing closed.

The pull request cannot change the decision

One job runs over the pull request with no secrets and only collects evidence. A second job, run by your organization, reads the rules from the protected branch, recomputes the result, signs it, and posts the check.

Anyone can verify the record later

The result is a signed statement recorded in a public log. Anyone can check it offline with cosign, a standard open-source tool, with no Siglum service involved.

Where Siglum fits in a pull request

What PASS means, and what it does not mean. PASS means the required checks ran to completion on this exact commit, under rules the author could not change during the run, and the result follows only from that evidence. It does not mean the code is safe, the tests are good, or the dependencies are sound.

From a green check to a signed result

Today, a contributor who can push a branch and edit CI can make a required check pass without doing the work it stands for. Nothing is forged, and the check really goes green. The audit shows where your repositories allow this. The gate prevents it.

Example: audit the demo repository

Real commands and output
siglum demo scaffold --out /tmp/gate-proof-demo --repo owner/gate-proof-demo --force
cd /tmp/gate-proof-demo
siglum audit --config siglum-audit-config.json

# Siglum evidence-gap audit: `owner/gate-proof-demo`

Found 1 gap(s):

| Severity | Code | Target | Detail |
|---|---|---|---|
| HIGH | PR_EDITABLE_WORKFLOW | `.github/workflows/ci.yml` | '.github/workflows/ci.yml' satisfies required checks ['tests'] but is editable in PRs; a head can rewrite its own gate |

echo $?
1

The demo writes a sample repository with one known gap: the workflow that produces the required tests check can be edited by the pull request it checks. On a real repository, siglum audit --repo owner/name reads branch protection, rulesets, and workflows the same way. It only reads and changes nothing. Exit code 0 means no findings, 1 means findings, and 2 means the audit could not finish.

PASS: the change may merge, with a signed record

Every required check gave a definite answer and none failed. The gate confirmed its own identity and its settings, and the signed statement was verified. Only then does the check turn green.

FAIL or ERROR: the gate blocks the merge

A skipped check, an unreadable rule file, an edit to a protected input, an approval left on an older commit, or a signing failure all block the merge. A comment on the pull request says why.

Two tiers

Dry-run runs in your normal CI and previews the result. Use it to write your rules and to find checks that skip without failing. It does not confirm its identity and does not sign.

Sealed is the protected setup. It runs in a workflow your organization controls, outside the pull request's own workflows. It confirms its identity with GitHub's OIDC token (a short-lived identity token that GitHub gives each workflow run) and signs the result. It protects against a contributor who can push and edit CI but has no organization admin rights.

Limits today. Siglum does not protect against a compromised organization administrator, who can turn enforcement off. This version runs one built-in check, a scan for leaked secrets, because checks that run the author's own code would need stronger protection than the design gives today. Signing uses Sigstore's test service (staging) and refuses the production service until that path is reviewed, so treat every signed record as a test record. Gating releases is a separate step you add yourself.

Try the audit, then deploy the gate

Start with the read-only audit and the local demo. Deploying the full gate needs a GitHub App that you register in your own organization.

  1. Install and audit.

    You need Python 3.12 or newer. Install from source, then run siglum audit --repo owner/name on a repository you can read. Private repositories need a GITHUB_TOKEN.

  2. Try the demo.

    siglum demo scaffold writes a sample repository with a known gap. The audit finds it, and siglum setup check --local . shows what a ready install looks like. No GitHub access is needed.

  3. Deploy the gate.

    Register your own GitHub App. Add the two workflows from the repository's workflows/ folder, pinned to a version contributors cannot edit, and store the App's id, installation id, and private key as secrets. Make the siglum check required and accept it only from your App. Then run siglum setup check against the repository before you rely on it.

Install

git clone https://github.com/siglum-dev/siglum && cd siglum
python -m pip install -e ".[dev]"

Audit and check a repository

export GITHUB_TOKEN=YOUR-TOKEN
siglum audit --repo owner/name
siglum setup check --repo owner/name --app-id APP-ID

Secrets the gate workflow needs

SIGLUM_GITHUB_APP_ID
SIGLUM_GITHUB_APP_INSTALLATION_ID
SIGLUM_GITHUB_APP_PRIVATE_KEY

Signing needs the sigstore extra (pip install -e ".[sigstore]"). If siglum is not found after install, add your Python user script folder (often ~/.local/bin) to PATH.

A good first test

Run siglum audit on three repositories you merge into every week. Read the findings with the people who manage branch protection (the GitHub settings that control what may merge). Then try the demo before you register an App.
