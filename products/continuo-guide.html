How continuo works

Continuo is a complete build studio for people who build with AI. It gives one builder or a small team, on their own machine, the jobs between a program and a product. You bring the ideas and your own agents and models. Continuo brings the roles, the line they form, the checks between them, the records, the cost control, and your decisions. This page describes the design for version 0.1 and says which parts exist in code today.

The main parts

Continuo has three layers. The line is the center: roles in order, with handoffs and checks between them. Guardrails and the producer sit under it: the sandbox, the publish gate, realms, budgets, the meter, and the schedule. The core holds the shared records, the rules for confirming work, and the store, and it makes no model calls. Anything that needs a model is done by your own agents.

The problem

A person with an AI coding agent can make a working program in an afternoon. A product is more: something a stranger can use, that is secure, stays up, is documented, was built for a real need, and keeps improving. In a company, a dozen jobs stand between a program and a product. The builder with an agent has none of them, and the agent does not know they are missing. It says "done" when the code compiles.

So the builder either plays every role from memory, late and partly, or skips the roles and ships. Both fail quietly. Continuo makes the missing jobs visible, defines each one from how the job is really done, runs work through them in order, and lets the builder's own agents do the labor under that definition.

The parts, in plain words

Role
One job, defined by its responsibilities: what it receives, what it decides, what it hands on, what it must never do, and the checks that show its work is complete. Each shipped role is copied from a real job, with the sources named. Version 0.1 ships 17 roles, from product manager to release manager.
Performer
Who does a role for one piece of work: a person, an agent, or continuo itself for checks a program can run. The record always says which. A role that reviews work never accepts the performer who made it.
The line
The order roles run in for one kind of work. A new product runs a long line, from the brief to the release. A bug fix runs a short one. Version 0.1 ships 10 lines: product, feature, fix, chore, spike (a short experiment), release, patch, rollback, a monthly learning line, and a weekly support digest.
Handoff
What one role gives the next: named files in a fixed format, in the project. The next role starts only when the handoff passes its checks.
Check
A program that runs on a handoff, such as "tests passed on this commit" or "no secret in the change". Version 0.1 ships 79 checks.
Review role
A role that makes nothing and can stop the line: code review, testing, security, accessibility, and license review. Its ruling holds for the exact files it reviewed, and the maker cannot overrule it.
Owner
The builder, or the team's lead for that product. Owners decide. Nothing that needs the owner's judgment is decided by a program or an agent.
Producer
The role continuo performs itself: schedule, scope, and cost.
Practices
A team's own additions to a role or a line: a rule, a check, a template, or a step. A practice starts on trial and is kept or dropped on evidence.
Realm
The kind of a project: personal, work, or sensitive (for example, one realm per client). Material from different realms never mixes.

The 10 lines

A line is the order the roles run in for one kind of work. Continuo ships ten, and you can edit them or write your own.

LineWhat runs, in order

How work moves along the line

Work enters a line in one of three ways: an agent writes a status item that names the kind of work, the builder opens it on the page, or a starter (a template for a new project), adopt (mapping an existing project onto a line), or a nightly job opens it. Each work item names its line and the line's revision, so a later edit to a line applies only to new items.

At each step, continuo issues an attempt (one try at one step by one performer) and writes a brief for the performer. It reads the handoff files the performer writes, runs the checks, and either moves the work on or sends it back with the findings. A returned step gets a set number of rounds, and then the owner decides.

A step that is skipped is recorded as skipped, with the owner's reason. Any later finding that the skipped role would have owned names the skip. Decisions that the owner owns arrive on the page one at a time, each with a recommendation and bound to the exact files the owner reads.

Inside, the line is a state machine. Each step instance has a state such as waiting, open, checking, returned, waiting on the owner, passed, skipped, or stale. One table of transitions says what each event does in each state. The rules are pure functions (code whose result depends only on its inputs), so they can be tested without a store, a clock, or git.

Built today as a model: the grammar for lines and its validation, the shipped roles, lines, handoffs, and checks, the transition table, acceptance and staleness, and the release rule. Eighteen scripted scenarios walk the shipped lines through it. The engine that runs these rules on real projects, with briefs and the line view, is planned for 0.1.

How continuo knows work is done

An agent saying "done" is not enough. Continuo confirms that the change exists and that a test or a check passed on the current code.

It does this in two steps. First it confirms that the commit or the file the agent named is really there. Then it looks for a program that showed the change works: a test, a check, a CI run (the automated checks on the code host), or a live check that covers the change and passed on the current code. The page shows work an agent only reported apart from work that was confirmed.

The rules are fixed and run without a model. Work counts as confirmed only when a program confirmed at least one piece of evidence and every check the agent cites passed on the current code. A timeout, an error, a crash, or a missing result never confirms work; it goes to you for review. A report is rejected only when evidence contradicts it. The owner can override a verdict, and the override is recorded.

A pass from before the latest change does not count. If the code moves after a check passed, the item drops back until the check runs again. Records name files by hash: a short fingerprint of a file's contents that changes when the file changes.

Built today: agents report work, evidence, and questions in a status file, and continuo checks the evidence. The current code uses an earlier, simpler form of these rules. The full rules, links between pieces of work, and a log that shows any later change are planned for 0.1.

How an agent performs a role

An agent never needs to know continuo. It sees a brief: a file with the role's definition, the handoffs it receives, the project's practices, the checks it must pass, and the outputs expected. The brief keeps two parts apart. Instructions come only from approved role, line, and practice files. Data is everything an agent or another person wrote, and it is marked as data that must never be treated as instructions. A brief has a size limit, 24 KB by default.

When a step is ready, continuo tells the open assistant session through a hook (a script the assistant runs at set points, such as after each tool call). An assistant without hooks reads a list of open steps at the start of its next session. The agent does the work and writes the handoff files. It never pushes, never holds a credential, and never decides what the owner owns. It can ask a question, and the answer comes back bound to the exact wording the owner read.

Continuo records how it knows who performed each attempt, from strongest to weakest: continuo started the run, the code host reported it, the person acted on the page, the session's own records show it, the person confirmed it, or a status file only says so. A reviewer must be far enough from the maker: a fresh context at least, and for client work a different model. A review in the same session as the work never opens a gate.

When continuo starts an agent itself, the agent runs in a sandbox: a closed environment that holds a copy of the repository with no remote, the brief, and the model tool's own login. Your home folder, git and code-host credentials, SSH keys, and other repositories are absent. Network traffic goes through a proxy (a relay that checks each connection) that allows only the model's service. In 0.1 a credential proxy adds the model login on the way out, so the agent holds no credential at all.

Built today on Linux: the sandbox, the network proxy, and the code that starts an agent and limits its run. Starting agents this way stays switched off until the 0.1 model runner, which adds the credential proxy and macOS support. Briefs for roles, hooks, and attestation (records of which session wrote which file) are planned for 0.1.

Release and the publish gate

The publish gate is the check every push passes through. Nothing reaches a remote repository without it. For an ordinary push it checks the identity and the account, looks for secrets in the commits, and checks that the change stays in its task's scope and has its evidence.

A release push (a version tag, or a branch that deploys) is allowed only when all four of these hold:

  1. The owner's authorization is bound to this exact push: the tag or branch, the commit, and the hashes of the release files.
  2. Every commit in the release belongs to a work item, comes from a trusted pull request review, or was accepted by the owner by its commit id.
  3. Every required step of every included work item has passed, was skipped with a recorded reason, or does not apply, with no review gone stale.
  4. Every assessment on the release (security, license, test, and accessibility where it is on) has passed, or is deferred by an emergency release within its deadline.

The gate records a release as published only when the remote is confirmed to hold it. A push that never arrives leaves its commits in the next release. The release line also has a rollback path. In 0.1, owner actions on the page are signed with a passkey or a security key, so an agent that can open the page still cannot act as the owner. A weaker mode for machines without a key is labeled as weaker.

Built today: the gate for actions of agents that continuo starts, and the release rule as a tested model. The gate on your own pushes, the release line against real git, and signed owner actions are planned for 0.1.

Realms

Each project is in a realm: personal, work, or sensitive. A consultant might keep one realm per client. Material from different realms never mixes in one brief, one task, or one report, and the publish gate cannot push one realm's code to another realm's remote.

A session is bound to a realm when it starts in a registered project or first reads a file in one. A session already bound to one realm is refused as a performer in a project of another. For work and sensitive realms, the central store keeps only ids, states, hashes, times, costs, titles, and decision questions. Other free text is read live from the project's own files and is stored only if the realm opts in.

The store never holds prompts, model responses, or file contents from your sessions.

Built today: each registered project names its realm. Named realms and the per-realm storage rules are being built.

The meter, budgets, and the producer

The meter reads your assistants' local session records and prices every model call it can see. It keeps four kinds of cost apart: billed use, the share of a subscription's limits, an estimate of the API price (marked "not billed"), and use it cannot measure. Every attempt gets a ledger entry with its role, model, cost, and outcome.

Each work item has an appetite: a time and a budget, prefilled by the kind of work. For agents that continuo starts, the budget is a hard stop: the most a run could cost is reserved before it starts, and the start is refused if any budget would be passed. For your own sessions, continuo cannot stop the assistant, so it warns you and adds an entry to the page's list of what needs you. Past the appetite's time, the owner decides whether to extend, stop, or cut scope. Continuo may propose a cut, but only the owner decides.

Built today: the meter for Claude Code and Codex, with a live view and a status line, and a refusal to start a paid run without a budget. More assistants, budgets per item and project, and the schedule are planned for 0.1.

The page and the session screen

The page is a local web page. It listens only on your own machine, needs a fresh access token each time it starts, and refuses requests from other sites. In 0.1 its main view is the line view: each open work item as a row of steps, each with its state, and each step opening to its attempts, checks, findings, and cost. The Needs you list shows the decisions waiting on you, oldest first, each with the role that asks, what it needs, why it matters, and the recommendation.

The session screen is a separate terminal program for builders who run several agent sessions at once, across containers on one machine. It lists every session with its environment, assistant, repository, and state, says which ones are waiting on you and why, and launches or attaches sessions in tmux (a program that keeps terminal sessions running in the background). It reads facts from each environment and never calls a model.

Built today: the page with what needs you, what changed since your last visit, and each project's plan against what is confirmed done. The session screen is being built: its local build is complete, and testing on real environments is under way. The line view is planned for 0.1.

How the studio learns

A practice is your own addition to a role or a line: a rule, a check, a step, or something an agent must never do. Each practice is written as a card: one instruction an agent can follow and a person can check.

A card starts on trial. Continuo measures whether agents followed it on real work and what it costs to carry, and you keep it or retire it. No number promotes a card by itself. Cards on trial or kept are written into the briefs of the role they belong to and into the instruction files your assistants read.

The advisor studies how your work went: which steps were sent back, which checks fail most, what was skipped, and what each passed step cost. It proposes new cards for you to approve. It runs inside the assistant you already use, so it makes no hidden model calls, and it never sets a result or relaxes a guardrail.

Continuo also reads a list of trusted outside sources, such as vendor engineering guides and tool changelogs, and turns useful items into candidate cards. An outside card goes through the same trial as your own. Each month, the learning line gathers cost, operations, support feedback, and your own notes into one view with proposals for what to fix or build next.

Planned for 0.1.

What continuo is not

Not an agent or a model
It writes no code and makes no judgment that needs a model. Your agents do the work.
Not a project tracker or a prompt library
Work moves through roles with handoffs, checks, and records. The line advances only on files, checks, and owner decisions.
Not a cloud service
It runs on your machine. A shared view across a team's installs is planned for after 0.1.
Not a replacement for your judgment
Every decision the owner owns waits for the owner, and no change that matters promotes itself.
