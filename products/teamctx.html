For developers who work through a coding agent

Know what changed before you touch a file.

Before you or your agent edit, teamctx tells you what changed, what conflicts, what failed, and what it could not verify, as source-backed evidence you can judge. There is no model in the content path.

After one onboarding command, team context appears by itself: before the first edit of each session, and again when something changes while you work. Nobody runs a command in daily use.

Four checks, from systems you already use

Open pull requests or merge requests touching your files, failing or unconfirmed checks on your branch, acceptance criteria that changed on the linked issue, and design docs that were superseded.

A green means checked

teamctx never folds a coverage gap into a clear. Where it could not look, it returns Unknown and names the gap, never a false all-clear.

Metadata only, no model

It reads titles, states, labels, timestamps, and changed paths; never bodies, comments, or patches. It normalizes, routes, selects, and renders the record and never reinterprets it.

Where teamctx fits in a coding session

A precise meaning for clear. Every configured check ran and found nothing in the way: no other open pull request touches your files, the linked issue's criteria are unchanged, the docs you rely on are current, and no check is failing. A source teamctx could not reach is reported as not checked, and silence after that means checked and unchanged within the interval.

From a hidden collision to a plain sentence

The expensive failure is confident wrong context: editing a file an open pull request is already changing, or building on a green CI that is actually red. teamctx reads the record and says what it found, in a sentence a person can act on.

Example: what appears before the first edit

Real renderer output
Before you start, here is what to handle first:
  • Open PR #7 changed src/auth/token.py: look at it before you edit so you don't undo
    each other's work (gh pr view 7 --repo acme/widgets)
  Also checked: the linked issue's criteria are unchanged (issue #42 from your branch
  name); the docs you rely on are current; no failing checks found.

From a branch named 42-fix-auth in a repository with a docs folder. Your own pull request for the branch you stand on is set aside with an FYI; a fork pull request still surfaces, on purpose.

Clear to start

Every configured check ran and found nothing in the way. The line lists what was checked, so a clear is a statement about coverage as well as findings.

Something to handle first, or a gap it could not close

An overlapping pull request, a red or unconfirmed check, moved acceptance criteria, or a superseded doc is named with the command to open it. A source it could not reach is reported as not checked, never as clear.

Drill into any finding

teamctx why pr:7 --path src/auth/token.py prints the full evidence for one finding, and teamctx open-source opens the record it came from. Selectors are the handles you see in the output: pr:N, issue:#N, path:X, doc:PATH, gate:NAME.

Bounded on purpose. No model and no agent runtime: teamctx informs; it does not act or decide. No broad search, summaries, or question answering. No productivity analytics or presence tracking. It does not read private messages, pull request bodies, or patches, and it writes nothing to your source systems.

Onboard once, then let it appear

teamctx is pre-release and installs from source. One command detects the repository, writes a shareable config, installs the Claude Code hook, and runs a live reachability check.

  1. Install and give it read access.

    pip install -e . from a clone. If the GitHub CLI is logged in, teamctx uses it; otherwise set GITHUB_TOKEN or point GITHUB_TOKEN_FILE at a file. GitLab and Atlassian tokens work the same way, and teamctx never stores the values.

  2. Run onboard.

    It writes .teamctx/config.json, installs the hook, adds the CLAUDE.md snippet, and reports your credential and a live check. It is idempotent, and --dry-run previews it.

  3. Turn on the other sources.

    Add the jira and confluence blocks to the committed config to check acceptance criteria and superseded pages there. Agents get the same answer over MCP.

Install

git clone https://github.com/teamctx/teamctx
cd teamctx
pip install -e .
teamctx onboard

Committed config

{
  "schema_version": "teamctx.project_config.v0",
  "work_start": {
    "repo": "acme/widgets",
    "forge": "github",
    "docs_root": "docs",
    "jira": { "base_url": "https://your-site.atlassian.net" }
  }
}

To reproduce what the hook shows by hand: teamctx work-start --path src/auth/token.py.

teamctx reads metadata only. It does not read pull request bodies, comments, or patches, and it does no broad search or summaries. The architecture reserves source families for other work trackers and for explicit chat handoffs; the live sources today are the four above.

A focused first evaluation

Onboard one repository where two people or two agents work on the same files. Open a pull request on one branch, start a session on another that touches the same path, and read what appears before the first edit.
