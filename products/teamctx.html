teamctx
Early release · Apache-2.0
v0.1.0 on PyPI · Python 3.12+

For developers who work through a coding agent, and the teams around them

See what your team changed before you or your agent edit a file.

teamctx tells you and your coding agent what the rest of the team is doing around the files you are about to edit. It checks open pull requests, failing checks, changed requirements, and replaced design docs, and links each finding to its source. After one setup command it appears in the session on its own, and when it cannot check something, it says so.

The problem. A coding agent, or a developer working through one, starts editing without knowing what the rest of the team is doing. It cannot see the open pull request that changes the same file, the check that is failing on the branch, the requirement that changed on the issue, or the design doc that was replaced. The conflict shows up after the work is done, when it costs the most to fix.

You get a command line tool, a Claude Code hook (a command Claude Code runs before the agent edits a file) that shows the context on its own, an MCP tool (a standard way for other agents to call outside tools), and one setup command that installs the hook and the config.

Conflicts show up before the work

Before the first edit, teamctx names any open pull request that changes the same files, any failing check on your branch, acceptance criteria that changed on the linked issue, and design docs that were replaced. Each line says what to open next.

You run no commands day to day

After teamctx onboard, the context appears in the Claude Code session before the first edit. While you work, it checks again at most every 90 seconds and speaks only when something changed.

A clear result means it checked

When teamctx cannot reach a source or cannot see everything, it says what it could not check. It never reports a gap as all clear. There is no AI model in the path: fixed rules give the same answer for the same record every time.

Where teamctx fits in a coding session

What clear means. Every check that is turned on ran and found nothing in the way: no other open pull request touches your files, the linked issue's criteria are unchanged, the docs you rely on are current, and no check is failing on your branch. A source teamctx could not reach is reported as not checked. After the first message, silence means teamctx checked again and nothing changed.

From a hidden overlap to a plain sentence

The costly mistake is working from wrong context: editing a file that an open pull request already changes, or building on a branch whose checks are failing. teamctx reads the record and says what it found in a sentence you can act on.

Example: what appears before the first edit

Sample output from the README
$ teamctx work-start --path src/auth/token.py
Before you start, here is what to handle first:
  • Open PR #7 changed src/auth/token.py: look at it before you edit so you
    don't undo each other's work (gh pr view 7 --repo acme/widgets)
  Also checked: the linked issue's criteria are unchanged (issue #42 from your
  branch name); the docs you rely on are current; no failing checks found.

From a branch named 42-fix-auth in a repository with a docs folder, wrapped to fit. teamctx found issue #42 from the branch name and says so. The hook shows the same message on its own. Your own pull request for the current branch is listed as a side note and is not flagged as a conflict.

Clear to start

Every check that is turned on ran and found nothing in the way. The message lists what was checked, so you know what the clear covers.

Something to handle first, or something it could not check

An overlapping pull request, a failing or unfinished check, changed criteria, or a replaced doc is named with the command to open it. A source it could not reach is named with the fix, such as a missing token.

Look closer at any finding

teamctx why pr:7 --path src/auth/token.py prints the full evidence for one finding, and teamctx open-source pr:7 --path src/auth/token.py opens the record it came from. The handles are the ones you see in the output: pr:N, issue:#N, path:X, doc:PATH, gate:NAME.

Teams can also add their own checks. The committed .teamctx/config.json can turn checks on or off for everyone, and it can point at simple record files, such as a freeze calendar, that teamctx reports like any other check. The output always names a check the team turned off. This is on the main branch and is not in a release yet.

Scope. teamctx informs. It does not act, decide, or block anything. It does no broad search, writes no summaries, and does not answer open questions. It does not track people, presence, or productivity. It reads short facts and acceptance criteria fields from the sources you turn on. It does not read pull request bodies, comments, patches, or private messages, and it writes nothing back to those systems. Today it works with github.com, gitlab.com, and Jira and Confluence Cloud.

Set it up once, then let it appear

One setup command finds the repository, writes a config file the team can share, installs the Claude Code hook, and runs a live check that teamctx can reach your code host.

  1. Install.

    Run pip install teamctx (Python 3.12 or later). Version 0.1.0 is on PyPI (the public Python package index). For the newest changes, such as team checks, install from a clone of the repository instead.

  2. Give it read access.

    If you are logged in to the GitHub command line tool, teamctx uses that login. Otherwise set GITHUB_TOKEN or GITLAB_TOKEN, or put the token in a file and set GITHUB_TOKEN_FILE. Jira and Confluence need ATLASSIAN_EMAIL and ATLASSIAN_API_TOKEN. teamctx never stores the values.

  3. Run onboard in your repository.

    teamctx onboard writes .teamctx/config.json, adds the hook to .claude/settings.local.json (your personal settings, so it does not run on teammates' machines), adds a short note to CLAUDE.md, and reports what it found. Running it again is safe, and --dry-run shows the changes first. Commit the config so teammates get the same checks.

Install and set up

pip install teamctx
cd your-repo
teamctx onboard

# or, for the newest changes, from source
git clone https://github.com/teamctx/teamctx
cd teamctx
pip install -e .

Committed config

{
  "schema_version": "teamctx.project_config.v0",
  "work_start": {
    "repo": "acme/widgets",
    "forge": "github",
    "docs_root": "docs",
    "jira": { "base_url": "https://your-site.atlassian.net" },
    "confluence": { "base_url": "https://your-site.atlassian.net",
                    "space_key": "ENG" }
  }
}

teamctx onboard writes the code host and the docs folder for you. Add the jira and confluence blocks to turn those sources on. To see by hand what the hook shows, run teamctx work-start --path src/auth/token.py. For other agents, install teamctx[mcp] and connect the teamctx-mcp server, which offers a work_start tool.

The design documents also describe sources that are not built, such as chat handoffs. The live sources today are the ones in the table.

A good first test

Set up one repository where two people or two agents work on the same files. Open a pull request on one branch. Then start a session on another branch that touches the same file, and read what appears before the first edit.
