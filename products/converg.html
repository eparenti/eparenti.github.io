For Ansible Automation Platform engineers

Verify the network after the change.

converg is an Ansible collection (a package of Ansible add-ons) that checks a network change after it runs. It works out the intended state from the tasks that actually ran, reads each affected device directly, and passes the run only when every change it checks is confirmed on the live network. Nobody writes a separate test.

The problem. Network automation reports success when its tasks finish, but that does not confirm the network is in the intended state. Checking means writing a separate test for every change, so many teams skip it or check by hand.

You turn on one recording setting and add one final play (a group of tasks in an Ansible playbook) at the end of the playbook. Your change tasks, inventory, and device connections stay as they are, and the same setup runs in an AAP (Ansible Automation Platform) job.

The tasks you already wrote say what to check

converg records each task as it runs and turns the supported ones into required checks. There is no separate test file to write or keep up to date.

It reads the devices themselves

After the change, it reads each affected device over that device's own connection and compares what it finds with the checks. It only reads. It never changes configuration.

Each result says exactly what was checked

A PASS names the devices and checks it covers. Tasks and fields that converg cannot check yet are listed as unclaimed, and an evidence file records every reading.

Where converg runs in an Ansible job

What a PASS means. Every required check in the locked scope was confirmed on the device, and the scope holds at least one check. An empty scope cannot pass. Tasks and fields that converg does not support stay listed as unclaimed, and a PASS says nothing about them.

Example: checking a new BGP neighbor

BGP (the protocol routers use to exchange routes) needs a working session between two routers. An Ansible task can finish while that session stays down. converg checks both the configuration and that the session reaches the Established state (up and exchanging routes).

Example: the change task

From the verification guide
- name: Add the neighbor on IOS
  cisco.ios.ios_bgp_global:
    config:
      as_number: "65001"
      neighbors:
        - neighbor_address: 10.100.0.2
          remote_as: "65002"
    state: merged
  when: inventory_hostname == 'ios-01'

The guide's full example also adds the matching neighbor on an Arista EOS router, then runs converg.verify.run in a final play on localhost. AS (autonomous system) is the number that identifies a network in BGP.

PASS: every required check is confirmed

The configuration matches, the session is Established, and every other check in scope is confirmed. The result names the devices and services it covered.

FAIL: a required check is not confirmed

A wrong remote AS, a session that does not come up in time, or a missing device reading blocks a PASS. In enforce mode the play fails.

It also checks what the change did not touch

This check is on by default. converg looks at the supported items outside the change that appear in the same device reads, such as other BGP sessions, and gives each one a status: PRESERVED, REESTABLISHED, HEALTHY_AT_READ, UNKNOWN, or REFUTED. Only REFUTED, which means the evidence shows the item was not kept, blocks the play.

A healthy final read proves health only at that moment. To show that a session stayed up through the change, converg needs timing evidence from the device or the optional converg.verify.baseline play, which reads the network before the first change. The baseline play also lets converg catch items that the run deleted.

Limits. converg checks the intent your automation expressed. It does not judge whether that design is right, test general reachability, monitor the network over time, or repair and roll back changes.

Add verification to the end of a playbook

converg has no published release yet. You build and install it from a copy of the repository, which needs access while the repository is private. In AAP, install it in the execution environment that runs the change.

  1. Install the collection.

    Build and install it from the repository. Use ansible-core (the Ansible engine) 2.19, 2.20, or 2.21 with a tested Python version, and the tested vendor collection versions.

  2. Turn on recording and add the final play.

    Enable the capture callback (the plugin that records each task as it runs) before the run starts. Put the final play after every change, and keep localhost in the inventory and in any limit.

  3. Choose what a FAIL does.

    enforce, the default, fails the play unless the result is a PASS. audit reports the result without failing the play. A check that cannot finish fails in both modes.

ansible.cfg

[defaults]
callbacks_enabled = converg.verify.capture

Last play, after your change plays

- name: Verify the network change
  hosts: localhost
  gather_facts: false
  roles:
    - converg.verify.run

Check the evidence later

ansible localhost -m converg.verify.check_evidence \
  -a "run_dir=.converg/<run id> evidence=converg-artifacts/converg-<run id>.json line='<the evidence line>'"

To try it without failing the job, set converg_mode: audit. converg does not change how your earlier tasks fail. An exit status of zero does not prove that converg ran, so read converg_result.status.

A good first test

Start with one supported BGP change on lab routers. Run one healthy change and one with a deliberate session failure. Review the result, the unclaimed list, and the kept evidence with the engineers who approve network changes.
