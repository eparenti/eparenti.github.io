For teams that need to show what was checked before work counts as done

Check work against your acceptance rules and keep the evidence.

Verdx checks whether work meets a project's acceptance rules. It runs the checks you list, records what happened, and returns one of four results: pass, fail, incomplete, or not applicable. You can replay any saved result later without running anything again.

The problem. Work is usually called done when someone ran the tests and said they passed. A test run that timed out or found no tests can look like a pass, files can change while the checks run, and later nobody can show what was checked.

You get a command line tool, a policy file (verdx.toml) where you list the checks, a saved receipt (the record of one run) for every attempt, and a plugin interface for checks written in Python. Markdown checks ship as the first plugin.

A slow or empty test run is never a pass

Pass needs every required check to finish and pass. A check that timed out is incomplete. A check that found no tests is not applicable. Results are never averaged into a score.

You can show what was checked, later

Each run saves the policy, a digest (a fingerprint of the contents) of every input file, each checker's output, and the decision. verdx replay recomputes the decision from that receipt without running any command or using the network.

Changes during the run are caught

Verdx takes digests of every file in scope before and after the run. If anything changed, the result is incomplete, so a receipt never describes code that changed during the checks.

Where verdx fits in a project

What pass means. Every required check finished and passed on the declared input files, and those files did not change during the run. Verdx reports coverage (whether each required check actually evaluated something) apart from the result. If one required check passes and another finds no tests or no matching files, the result is incomplete.

From a failing check to a replayable receipt

The repository's own example has one rule: a file must contain 42. It holds 41, so the first check fails. After a repair the second check passes, and the first receipt still replays as a failure.

Example: fail, repair, check again, replay

Real commands and output
cp -R examples/acceptance /tmp/verdx-acceptance-example
uv run verdx check /tmp/verdx-acceptance-example --output text

FAIL  Required coverage: full
  expected-value: fail (required, coverage full). command exited with 1
  expected-value: command exited with 1
Evidence: /tmp/verdx-acceptance-example/.verdx/runs/<run-id>/receipt.json

python3 /tmp/verdx-acceptance-example/repair.py
uv run verdx check /tmp/verdx-acceptance-example --output text

PASS  Required coverage: full
  expected-value: pass (required, coverage full). command exited with 0

uv run verdx replay /tmp/verdx-acceptance-example/.verdx/runs/<first-run-id>/receipt.json --output text

FAIL  Required coverage: full

Run these from the verdx repository after install. The first check exits 1 and prints the receipt path. Replaying the first receipt still reports the failure, though the file is now repaired, because replay reads only the saved receipt. Each check also prints a decision hash, left out here.

Pass: the work is accepted

Exit code 0. The receipt is the proof. Copy the run folder anywhere, and verdx replay recomputes the same decision from it.

Fail or incomplete: the work is not accepted

A required failure exits 1. Missing evidence, a command that could not finish, or input files that changed exit 2 (incomplete). Not applicable exits 3. If a check reports a failure and incomplete coverage together, both stay visible.

Plugins and the older scored commands

A domain plugin (a Python package that adds checks for one kind of file) can supply checks. Markdown checks for heading order, relative links, and whitespace ship as a plugin, and an example plugin is a template for your own. Plugins register through a Python entry point (the standard way for a package to announce a plugin) and use only the public interfaces.

The older validate, fix, and drive commands give a scored pass-or-block result and can run repair loops with a set limit on attempts. A scored result can pass with findings. Use check when a rule must pass with no findings and you need a saved receipt.

Limits. Receipts are unsigned files kept on your machine. Replay proves that a receipt is consistent with itself. It does not prove who made the receipt, and it cannot detect someone who rewrites both a receipt and its hashes. The fingerprints cover only the declared local files. They do not cover remote services, the wider environment, or files a command reads outside that scope. For signing and enforcement the author cannot bypass, use a trusted gate in CI (the automated checks that run on each change), such as Siglum.

Add acceptance rules to one project

Verdx is an early implementation. It has not been published as a package, so you install it from source. It needs Python 3.13 or later, and command execution is tested on Linux.

  1. Install and check verdx itself.

    Clone the repository and run uv sync --locked --extra dev (uv is a Python package manager). Then uv run verdx check . runs the repository's own policy: lint, formatting, type checks, tests, and documentation checks. The project's own automated checks run the same policy.

  2. Write verdx.toml.

    List the files that affect results in include, including lockfiles and checker source. Give each check a list of arguments. Add a timeout if the default of 300 seconds is wrong, a version_command to record the tool's version, and exit-code lists where the tool needs them.

  3. Keep and replay the receipts.

    Each run gets its own folder under .verdx/runs/. Copy a complete run folder to move the evidence. verdx replay returns the original decision's exit code.

Install

git clone https://github.com/ostinato-forge/verdx.git
cd verdx
uv sync --locked --extra dev
uv run verdx check . --output text

verdx.toml

version = 1
include = ["src/**", "tests/**", "README.md", "pyproject.toml", "uv.lock", "verdx.toml"]

[[checks]]
id = "tests"
command = ["uv", "run", "--locked", "pytest", "-q"]
version_command = ["uv", "run", "--locked", "pytest", "--version"]
timeout = 300
not_applicable_codes = [5]

[[checks]]
id = "readme"
domain = "markdown"
target = "README.md"

[[checks]]
id = "style-advice"
command = ["uv", "run", "--locked", "ruff", "check", "src/"]
required = false

Check and replay a project

uv run verdx check /path/to/project --output text
uv run verdx replay .verdx/runs/<run-id>/receipt.json --output text

Exit code 0 means pass and 1 means failure. Any other code means incomplete unless success_codes, failure_codes, or not_applicable_codes say otherwise. Pytest returns 5 when it finds no tests. Output is JSON when piped and text in a terminal.

Results and exit codes
ResultExit codeMeaning
pass0Every required check completed and passed
fail1A required check found a failure; other coverage gaps stay visible
incomplete2Required evidence is missing, a command could not finish, or input files changed
not_applicable3No required check evaluated any applicable work

The input fingerprints skip a fixed list of generated folders, such as .git, .venv, node_modules, and caches. This list does not read your .gitignore file. The receipt format is versioned, and verdx rejects unknown versions.

A good first test

Write a policy with your test suite as the one required check and your linter as advisory. Run it, break a test, run it again, then replay both receipts from a copy of the run folders.
