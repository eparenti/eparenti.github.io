For researchers and engineers who build AI agents

Can an agent rely less on its model over time?

Just-in-Time Cognition is a research program. It asks whether some of what an AI model does inside an agent can move into explicit parts that people can inspect: a written task contract, recorded evidence, tools with fixed permissions, and saved procedures that state when they apply. If that works, an agent would need the model less on familiar work, and every accepted result would carry its evidence.

The problem. In most AI agents today, the model suggests each step, judges whether its own work is done, and decides what to run. Nobody can inspect why a step worked, and what worked once is not kept in a form that can be checked again. Claims that agents can depend on the model less are rarely tested against failure rules written in advance.

The repository holds the research argument, a hostile review of it, a formal model, an experiment plan, and a small working core in Python. It keeps three kinds of claim apart: what the code guarantees today, what needs controlled experiments, and a long-term idea.

Tested now: the core's guarantees

The core accepts a claim only when a separate check supports it, runs only the commands a contract allows, and withdraws results when something they depend on is withdrawn. Tests cover these rules on a fixed set of cases.

Open: better agents from contracts

Whether contracts and recorded evidence make agents more reliable or cheaper is a hypothesis. It needs controlled experiments on real tasks, and none has run yet.

Long term: less need for the model

Saved, checked procedures might lower how much an agent depends on the model across a stream of tasks. The repository states this only as a possibility and lists in advance the results that would show it is wrong.

How the core handles one task

What the passing tests mean. They show that this code follows its own rules on the cases tested, including every sequence of four events from a fixed set and real command runs. They do not show that a verifier is correct, that a contract is well written, that all dependencies are declared, that the command is isolated, or that the research idea is right.

What was run, and what it found

So far the core has run one real command, and two constructed experiments have tested the measuring tools. No experiment on real tasks has run. The numbers below come from cases built on purpose to check that the measurements react as designed.

Example: run the core on its own test suite

Real commands
# fingerprint the input files the contract lists
PYTHONPATH=src python3 -m jitc examples/kernel-self-check.ecir.json \
  --repo . --measure-environment

# run the contract: one allowed command, the test suite
PYTHONPATH=src python3 -m jitc examples/kernel-self-check.ecir.json \
  --repo . --allow-executable python3

The example contract allows one command, python3 -m pytest -q, so pytest must be installed. At revision 009ba86 the fingerprint saved in the example no longer matches the files, so the run stops before the command starts, with the error measured repository environment does not match command. That is the admission check (the step that decides whether a result is accepted) at work. To run it, copy the measured value into the three places the example stores it: the environment object, the policy, and the command. --allow-executable is your own choice of which program may run. The contract cannot grant it.

What would support the idea

The strongest result the plan names: across saved versions of the procedure library, both the cost of the strong model and the loss from swapping it out fall, while results on new tasks held back for testing stay as good. Only that result would show that skill has begun to move out of the model.

What would show it is wrong

The plan lists twelve kill criteria (results that count against the idea, written before the experiments). Examples: the full system does not beat a matched strong agent; savings disappear once all costs are counted; reuse helps only on exact repeats; or swapping out the model hurts as much as ever while the library grows.

The four stages of the plan

Stage A tests the core's rules with hand-written contracts. Stage B asks whether there is enough repeated work for reuse to help, if expert procedures were perfect. Stage C would build procedures automatically from past work. Stage D would replace the model with weaker ones and measure what is lost. Stage A is in code. Stage B has run only on constructed cases. Stages C and D are not built.

Claims the project does not make. It does not claim intelligence without prior knowledge, truth about the open world, reasoning free of assumptions, or that pretrained models will soon be unnecessary. The pilot runs changed code with no operating system sandbox (a locked-down space for untrusted code), so it is safe only with the repository's own fixed cases.

Read the argument, then run the core

The notes carry the argument and the code carries the tested rules. The code needs Python 3.11 or later, and the tests need pytest.

  1. Read the stress test first.

    It is a hostile review of the idea: its objections, the fixes it requires, the baselines (simpler methods the idea must beat), and the kill criteria. The working note and the research proposal hold the original idea and its first formal write-up.

  2. Read the formal core and the experiment plan.

    The formal core defines the state, the allowed changes, and six guarantees, each with the assumptions it needs. The experiment plan sets out the four stages, the baselines, and the kill criteria.

  3. Run the tests and the experiments.

    python3 -m pytest runs the 33 tests. jitc.experiment runs the Stage B check and jitc.repository_pilot runs the pilot. Both print their results as JSON.

Tests

git clone https://github.com/ostinato-forge/jit-cognition.git
cd jit-cognition
python3 -m pytest

Experiments

PYTHONPATH=src python3 -m jitc.experiment --include-outcomes
PYTHONPATH=src python3 -m jitc.repository_pilot

--include-outcomes adds a record for each task. The interactive page docs/jit-compiler-visual.html shows the design, the trust boundaries, one run step by step, how a withdrawn input cancels what depended on it, and the research stages.

How to engage

Read the stress test and look for a way the idea could pass the kill criteria without being true. Then measure the example's inputs, update the contract so it runs, change one input file, and watch the next run be refused.
