For people who run two AI agents on one project

Let two AI agents work together on one project.

agent-collab lets two coding agents share one codebase with clear roles. One agent, the architect, plans tasks and reviews pull requests. The other, the builder, writes the code and opens the pull requests. Every task, hand-off, and review decision is saved in files in the repository, and a small local message service tells each agent when it is its turn.

The problem. When two coding agents work on one codebase, nothing records who is doing what. They coordinate through chat or through the person running them, lose their place after a restart, and a change can merge with no review on record. The person ends up passing messages between the agents.

You get one Python script for the task workflow, a local broker (a small server on your own machine that passes short messages between agents) with a command line client, and a written protocol that both agents follow.

The record survives a restart

Each task is a file under .collab/tasks/ with its owner, its test command, its acceptance criteria, the hand-off summary, the pull request link, and the review decision. An agent that restarts reads the files and picks up where it was.

Each agent knows when it is its turn

The broker passes short signals such as task claimed, pull request ready, and merged. An idle agent waits with recv --wait 60 and wakes when a message arrives, so nobody has to check files or relay messages by hand.

Every change goes through review

The builder works on one branch per task and opens a pull request. The architect reads the diff (the line-by-line changes), records approve, changes requested, or blocked, and merges after the decision is on record.

How the two agents share the work

What each task leaves behind. One task file with its owner, test command, acceptance criteria, hand-off summary, pull request link, and review decision, plus a review note under .collab/reviews/. check-stale flags a task in progress or in review with no activity for 24 hours. doctor reports whether a role's identity, git hooks, daemon, and sync are healthy.

From a task file to a merged pull request

The architect writes the task with a test command and acceptance criteria. The builder claims it, builds it, runs the test command, pushes, and hands off with the pull request link. The architect reviews and records the decision.

Example: one task, start to finish

Real commands
python3 scripts/collab.py new-task "Add retry to the fetch client" \
  --created-by architect --assigned-role builder \
  --verify-cmd "pytest -q" --file src/fetch.py --accept "tests pass"
python3 scripts/collab.py claim TASK-001 --actor builder
python3 scripts/collab.py verify TASK-001 --actor builder
python3 scripts/collab.py handoff TASK-001 --actor builder --summary "done" --pr-url <url>
python3 scripts/collab.py review TASK-001 --actor architect --decision approve --summary "lgtm"
python3 scripts/collab.py complete TASK-001 --actor builder --summary "merged"

verify runs the task's test command. status summarizes the queue, and next --role builder shows what is waiting for a role.

Approved and merged

The review decision is on record, the architect merges the pull request, and complete closes the task with a summary.

Changes requested, blocked, or stale

The builder fixes the feedback on the same task. If two review rounds do not settle it, the task is marked blocked and goes to the person in charge. check-stale flags work with no recent activity, so nothing waits unnoticed.

How strict the sync checks are

enable --enforce sets one of three modes: off, warn, or hard. In hard mode, handoff, review, and complete refuse to run when the role's daemon has stopped reporting or its git state is out of date. --allow-unsynced overrides that once and leaves a note in the task history.

Where it stands. Built and used on one private product in spring 2026. The protocol, the broker, and the command line work. The project is stable and is not under active development. It supports exactly two roles, one architect and one builder. Move the broker off your own machine's address or turn off the token only if you accept the risk.

Add it to a repository

It needs only Python 3 and its standard library. Copy one script into your repository, set up the workspace, and start the broker in a second terminal.

  1. Copy and set up.

    Copy collab.py into your repository's scripts/ folder and run init to create .collab/. Add .collab/ to .gitignore: it holds working state and stays out of commits.

  2. Turn on sync checks for each role.

    enable records the role's identity under .collab/runtime/, installs git hooks (scripts git runs on checkout, commit, merge, and push), and saves a first sync point. Run doctor to check the setup, and run daemon up in its own terminal to keep the sync record current.

  3. Start the broker.

    brokerctl.py up starts the broker with a token and saves the token in a per-user file, so other agents on the same machine can connect. onboard prints a one-screen quick start for a role, which you can hand to the agent.

Workspace

git clone https://github.com/ostinato-forge/agent-collab
cp agent-collab/collab.py /path/to/your-repo/scripts/collab.py
cd /path/to/your-repo
python3 scripts/collab.py init
python3 scripts/collab.py enable --role builder --actor builder \
  --peer architect --enforce warn
python3 scripts/collab.py doctor --role builder
python3 scripts/collab.py daemon up --role builder

Broker

cd /path/to/agent-collab
python3 brokerctl.py up
python3 brokerctl.py onboard --role builder
python3 brokerctl.py recv --role builder --wait 60

An agent waiting on recv --wait 60 does not stop other agents from sending messages or reading the history. AGENT.md in the repository is the short brief to give each agent, and docs/protocol.md is the full workflow.

The project is stable and is not under active development. The automated tests run on Linux and macOS. Windows is not tested.

A good first test

Run one small task through the full loop with two agent sessions: new-task, claim, handoff with a real pull request, review, merge, and complete. Then read the task file and the broker history.
