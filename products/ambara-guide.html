How Ambara works

Ambara keeps the project facts that coding agents need (decisions, workflows, handoffs, and status) in a git repository. It serves them to agents at the start of each session and sends lasting changes through review. This page explains how it works, from storage to release checks.

The whole system

Ambara has three parts: a git repository that holds the context, a server that picks what to show, and the agent tools that read it.

Each piece of context is a Markdown file with frontmatter (a short block of labeled fields at the top of the file). Because the files live in a normal git repository, every change has a history, an author, and a review. The Ambara server indexes the files (builds a searchable list of them), ranks and filters them for the current project, and checks them for secrets. It serves the result over MCP (the standard way coding assistants connect to outside tools) or writes it to a plain file that any agent can read.

What the agent can do

The agent calls these MCP tools for you, so a person never needs to learn them. The server offers 17 tools at this revision.

Entry types and how each is saved

Each entry has one of five types, and the type decides how a save is written.

active
A short-lived handoff, such as "Left off at the token endpoint." It is written at once to a short-lived branch and expires, after 72 hours by default.
project
Current project status, such as "Auth migration is in flight." Saving one opens a light review request.
decision
A team decision, such as "Use gRPC for internal services." It is proposed on a review branch.
workflow
A recurring team process, such as "Run validation before review." It is proposed on a review branch.
principle
A lasting standard, such as "Restricted data stays out of context entries."

Review requests open as GitHub pull requests or GitLab merge requests. On other git hosts Ambara creates the branch only. When it creates only a branch, its reply says that no review request was opened.

Context goes stale, so Ambara includes a cleanup job (python -m ambara.curation.run_hygiene) that a team can run on a schedule. It opens review branches that expire old handoffs and mark lasting entries for a second look. Agents also get short notes inside context() about entries they should not rely on.

The startup summary and the savings receipt

The startup summary is short on purpose. It lists the entries that match the project, and it leaves out their full text until the agent calls read() for one it relies on.

Each summary includes a savings receipt: how much text Ambara sent, what it held back, and an estimate of the tokens (the units models count text in) saved compared with sending every eligible entry in full. A local record of these totals is on by default, so ambara value can show the running estimate.

Savings figures are estimates of the text Ambara itself sends, given as a low and a high value. They do not cover the whole session, caching, or the bill. A money figure appears only when a team sets its own token price.

Secret scanning and the content check

Every save and every startup summary passes a content check first.

  • Text that matches known password and key formats is blocked or blanked out before it is saved or shown.
  • Personal, confidential, or staff terms that a team configures send the entry to review.
  • Text from pull requests and issues passes the same central check before the agent sees it.
  • Commit capture applies the same content check as a save from the agent. So does the newer promote command.

The README calls security, privacy, and secret scanning release gates: checks that must pass before a release ships.

Outside sources

Ambara can show labeled pull requests, merge requests, and issues to the agent as context, and its core decides what is safe to show.

Each outside service has a provider (a small adapter that reads that service). A provider turns the service's data into short, labeled items. Ambara's core then applies the safety rules, limits how much text each source may add, records where each item came from, and renders it. The agent sees each item tagged with a suggested action, such as continue, reuse, revise, pause, hand off, or clarify.

LevelSourcesWhat is supported
SupportedGitHub, GitLab, Jira, local sample filesIncluded and on by default. Each passes the central safety rules and reports its own health, and has health and test commands.
Sample data onlyLinear, ConfluenceIncluded and on by default for offline tests with sample data. Ambara does not read their live services yet.
Not supportedNotion, Slack, Teams, Sentry, Google Docs and Drive, FigmaEach one needs its own privacy checks and sample data before any support is claimed.

The core applies these rules to every provider: text that looks like a credential is blanked out, unsafe links are removed, people's names are left out by default, excerpts are kept short, outside text is treated only as information for the agent to weigh, and a source that cannot be reached is shown as unavailable or stale. A provider cannot turn these rules off.

Commit capture in CI

A commit message can file an entry when its first line starts with ambara:. Adding (decision), (workflow), or (principle) after the word sets the type; without it, the entry is a status update.

ambara(decision): Use gRPC for internal services

In CI, the capture step downloads the context repository, signs in with a token if one is given, and checks each new commit message. Each entry passes the same content check as a save from the agent. GitHub uses the action that ships with the repository. GitLab CI and other systems run the same command directly:

ambara_capture:
  image: python:3.12
  variables:
    AMBARA_KNOWLEDGE_REMOTE: https://gitlab.com/your-org/team-context.git
    AMBARA_KNOWLEDGE_TOKEN: $AMBARA_KNOWLEDGE_TOKEN
    AMBARA_MAIN_BRANCH: main
  script:
    - pip install git+https://github.com/ostinato-forge/ambara.git
    - python -m ambara.action.capture

Capture reads only commit messages marked with ambara:. It does not collect anything else in the background.

Privacy boundary

Ambara stores only what someone asks it to save, and it keeps no record of what agents read. It has no code that collects search text, reading patterns, editor activity, or who took part.

  • The savings receipts and the local totals record token estimates and counts only.
  • They store no search text, replies, excerpts, caller names, or per-entry read records.
  • Ambara is not a secrets manager, a monitoring product, an agent runtime, or a meter of total model cost.
  • It does not prove who read what, guess who is online, skip git review, or replace human review of lasting project knowledge.

How releases are checked

Releases are checked on a local computer, with no calls to live workplace services. Checks from source run first, then a check of the installed package, then a container check.

uv run pytest -q
uv run ruff check .
uv run mypy src
env UV_CACHE_DIR=/tmp/ambara-uv-cache uv lock --check

scripts/installed-user-path-smoke.sh
scripts/docker-install-smoke.sh

The first four commands run the tests, the style checks, the type checks, and a check that the pinned dependency list is current. The installed-package script builds a package, installs it into a clean environment, and runs the demo proof. It also tests the source health commands and the safety rules, the Linear and Confluence sample data, and the plain file path for Claude Code, Codex, Cursor, and Gemini. The container script runs the command line tool as an ordinary user in Docker or Podman and repeats the demo proof. It covers one computer only. CI also runs the tests on Python 3.12, 3.13, and 3.14.
