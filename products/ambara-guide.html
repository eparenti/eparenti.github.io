How Ambara works

Ambara is the shared project context layer beside an agent's private memory. Project facts that need provenance (decisions, workflows, handoffs, constraints, status) live in git, durable updates are reviewable, and every write is explicit.

The whole system

Context lives in a git repository of Markdown files with YAML frontmatter. The Ambara server indexes, ranks, and filters it, applies privacy filters and secret scanning, and serves it to agents over MCP (the protocol that lets AI coding tools connect to external tools) or through a plain context file any agent can read.

What the agent can do

The agent calls tools; the person never learns an API. These are the tools the MCP server exposes at this revision.

ToolPurpose
startup()Relevant context before working. The recommended entry point.
context()Relevant decisions, project state, and project source inputs.
sync()Refresh the local index from the context repository.
read() / read_many()Full text for entries the agent directly relies on.
query() / search()Deep-dive on a topic, or keyword search across all entries.
record()Save a handoff, project update, or active note.
propose()Save a decision or workflow for team review through a review branch or request.
promote(artifact_id)Promote a labeled source artifact (a pull request, issue, or page) into durable reviewed knowledge. Dry-run by default.
hygiene() / expire()Lifecycle advisories for stale context, and marking an entry expired.
feedback(entry_id, signal)Mark context as useful, noisy, stale, duplicate, or pinned locally.
explain() / status() / validate()What Ambara does and does not track; connection health and sync state; schema and constraint checks.

Entry types and their write paths

active
Short-lived handoffs. "Left off at the token endpoint." Expires automatically.
project
Current project state. "Auth migration is in flight."
decision
Reviewed team decision. "Use gRPC for internal services." Goes through the reviewed path.
workflow
Recurring team process. "Run validation before review." Goes through the reviewed path.
principle
Durable standard. "Restricted data stays out of context entries."

Decisions and workflows are proposed on a review branch. GitHub pull requests and GitLab merge requests are first-class review backends; other git hosts fall back to branch-only. If Ambara only created a branch and did not open a review request, it says so.

Context needs maintenance. Ambara generates cleanup review branches that expire stale handoffs and flag durable entries for revalidation, and agents get quiet advisories inside context() so they know not to rely on stale entries.

Startup packets and the value receipt

A startup packet is compact on purpose. It carries the entries that match the project, with full bodies deferred until the agent calls read() for one it relies on. Each packet includes a value receipt: the size of the Ambara payload, what was deferred, and an estimate of tokens avoided compared with a full dump of eligible context.

A local aggregate value ledger is on by default, so ambara value can show the savings captured ambiently while you worked.

Reported savings are Ambara app-payload estimates with conservative low and high ranges. They are not total client, session, or cache billing, and not measured tokenizer truth. Currency estimates appear only when a deployment supplies its own token price; Ambara never invents a universal dollar value.

Secret scanning and the policy gate

Write and render paths run policy checks before durable writes and before startup output.

  • Known credential-shaped patterns are blocked or redacted before they reach durable writes or startup rendering.
  • Configured PII, confidentiality, and personnel patterns require review.
  • Source text from review artifacts and issues is normalized through the central policy path before surfacing.
  • Commit capture and CI capture apply the same content-policy gate as interactive writes, beyond regex secret scanning.

Security, privacy, and secret scanning are release gates for this product. They are not optional hardening.

Project sources

Ambara can read labeled GitHub pull requests, GitLab merge requests, and Jira issues and surface them as project context: continue, reuse, revise, pause, handoff, or clarify. Providers translate external APIs into bounded source artifacts; the core owns central safety, identity minimization, body policy, token budgets, provenance, cache health, and rendering.

TierSourcesSupport promise
First-class Source Previewgithub, gitlab, jira, fixtureShips in core, registers by default, flows through central safety, per-source health, doctor and smoke commands, conformance tests, and installed proof.
Fixture-backed public previewlinear, confluenceRegisters by default and supports no-network smoke and conformance fixtures. Live API fetch is not claimed.
DeferredNotion, Slack, Teams, Sentry, Google Docs and Drive, FigmaNot supported. Each needs separate product claims, bounded selectors, privacy proof, and fixtures first.

Core-owned enforcement applies to every provider: credential-shaped text is redacted, unsafe refs and URLs are removed, identity defaults to omitted, body policy is enforced before rendering, excerpts are capped by source budget, external text stays untrusted evidence, and an unavailable source stays visible as unavailable or stale. Providers translate; they cannot bypass the privacy rules.

CI capture

Commit-driven capture bootstraps the knowledge repo from the declared remote, applies forge-aware authenticated remotes when a token is provided, fetches the main branch, and evaluates explicit ambara: commit messages with the same content-policy gate as interactive writes. GitHub uses the bundled composite action. GitLab CI runs the entrypoint directly.

ambara_capture:
  image: python:3.12
  variables:
    AMBARA_KNOWLEDGE_REMOTE: https://gitlab.com/your-org/team-context.git
    AMBARA_KNOWLEDGE_TOKEN: $AMBARA_KNOWLEDGE_TOKEN
    AMBARA_MAIN_BRANCH: main
  script:
    - pip install ambara
    - python -m ambara.action.capture

This is for explicit capture markers and related workflow capture. It is not a generic background collector.

Privacy boundary

Ambara does not log what agents read, track who is online, or create activity feeds. Durable shared context only stores what you explicitly ask it to save. There is no collector for query text, read patterns, editor activity, or participation data; the system cannot track what it was never built to capture.

  • Value receipts and the local ledger record aggregate token estimates and omission counts only.
  • No query text, response text, body snippets, caller identity, or durable per-entry read receipts are stored.
  • Ambara is not a secrets manager, observability product, agent runtime, or total model cost meter.
  • It does not prove who read what, infer presence, bypass git review, or replace human review for durable project knowledge.

How releases are proven

The release proof is local and uses no live workplace APIs. Source checkout gates run first, then an installed-wheel smoke, then a container smoke.

uv run pytest -q
uv run ruff check .
uv run mypy src
env UV_CACHE_DIR=/tmp/ambara-uv-cache uv lock --check

scripts/installed-user-path-smoke.sh
scripts/docker-install-smoke.sh

The installed smoke builds a wheel, installs it into a clean environment, runs the demo proof, smokes source doctor and safety paths, verifies the fixture-backed Linear and Confluence previews, and simulates Claude Code, Codex, Cursor, and Gemini through the file-adapter path. The container smoke runs the installed CLI as a non-root user and repeats the demo proof; it proves a single-node install path only.
