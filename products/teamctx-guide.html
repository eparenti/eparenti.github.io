How teamctx works

teamctx shows you and your agent the current state of the tools your team already uses, before the first edit. There is no AI model between the source and what you read. teamctx collects the facts, applies fixed rules, and prints the result. It does not interpret what the record means.

The whole system

Connectors read the sources. A core of fixed rules decides what to say. Three surfaces show the same answer.

What a check is

A check is one question about the work you are about to do, answered from the source that holds the record. Each check gives one of three results, and each result line carries the evidence behind it.

Overlapping change
Another open pull request (GitHub) or merge request (GitLab) changes a file you are about to edit. Your own pull request for the branch you are on is listed as a side note. A pull request from a fork still counts as an overlap.
Check status
A check or pipeline on your branch is failing, still running, skipped, or canceled. Anything short of a finished success is reported as not yet confirmed.
Acceptance criteria changed
The criteria on the linked GitHub or Jira issue changed after you started. Acceptance criteria are the conditions an issue says the work must meet.
Doc replaced
A document in your docs folder names a newer replacement, or a Confluence page carries the teamctx.superseded_by property.
Team checks
Checks your team defines in the committed config, fed by simple record files such as a freeze calendar. These are on the main branch and not in a release yet.
Source unavailable
A source could not be reached, or had more results than teamctx could read. This is its own finding. It is never counted as clear.

The three results are clear, in the way, and not checked with the reason. A clear means the check ran. Where teamctx could not look, it says so.

Finding the issue and the start time

teamctx works out which issue you are working on by itself. It reads the branch name (a Jira key such as PROJ-123, or a GitHub issue number such as 42), commit messages (such as Fixes #42), and the point where your branch left the base branch. The output says how it found the issue, so you can judge it. --issue and --since name them by hand when the branch does not.

teamctx work-start --path src/auth/token.py
teamctx why pr:7 --path src/auth/token.py
teamctx open-source pr:7 --path src/auth/token.py

The handles after why and open-source are the ones you see in the output: pr:N, issue:#N, path:X, doc:PATH, gate:NAME.

Sources and what each one reads

A connector is the part that talks to one source. Each connector asks for a small, fixed set of fields.

Source typeBuilt todayWhat it readsWhat it leaves out
Code reviewGitHub, GitLabOpen pull requests and merge requests: numbers, times, branch names, changed files; checks and pipelinesBodies, comments, patches, broad search. Pull request titles are off by default
Work trackerGitHub issues, JiraAcceptance criteria fields and their change timesComments, user data, search history
DocsLocal docs folder, ConfluenceReplacement markers and timestampsFull page text, whole-space copies
Team recordsCommitted JSON filesThe fields the config namesFiles outside the repository, files not committed

Connectors have fixed limits on how much they read. Confluence, for example, reads at most 500 pages of a space. When a limit is reached, teamctx reports the check as partly done. It never reports a partial read as clear.

The design documents describe more than is built. They plan a policy gate (filters for secrets and personal data, proof that the requester may see each record, and audit logs) and more sources, such as other work trackers and chat handoffs. None of these exist at this revision. Today the protection comes from reading only the fields above, and from writing every sentence from fixed templates.

Why the same inputs give the same answer

A replay always matches because the rules core is pure code: it does not read files, use the network, start other programs, read the clock, or use random numbers. It receives the facts, the config, and the time as inputs. All reading and writing happens in the connectors, the command line, and the servers.

So the same inputs always give the same result. The test harness relies on this.

Trust model

Text that comes from a source is untrusted data. That includes pull request titles, issue text, and doc text. It must never become an instruction for an agent or a tool. The design keeps three kinds of text apart in each finding:

message
The sentence teamctx writes from a fixed template. This is what you read.
source excerpt
Optional evidence from the source, shown as data and never as an instruction.
reason
The rule that made the finding appear.

Trusted inputs are your local config, the connector settings, the fixed rules, and the answers the sources give about access.

Three surfaces, one answer

There are three ways to see the answer. All three come from one result, so they cannot disagree.

The Claude Code hook

Installed by teamctx onboard, or alone by teamctx install-hook. It runs before the agent edits a file. It shows the context before the first edit of a session, checks again at most every 90 seconds by default, speaks again only when something changed, and repeats a known gap at most every 15 minutes. It never blocks an edit. If teamctx hits an error, the hook stays silent.

The command line and MCP

teamctx work-start shows by hand what the hook shows, why prints the evidence for one finding, open-source opens the record, and status reports what is set up and what is missing. Other agents can call the same check through the work_start tool on the teamctx-mcp server.

The note that teamctx onboard adds to CLAUDE.md tells the agent how to use what appears. In a setup that does not run hooks, it tells the agent to run teamctx work-start before editing.

How the claims are tested

A test harness drives the real command line, hook, and MCP tool through 22 scripted scenarios against fake GitHub, GitLab, Jira, and Confluence servers that ship with the repository. Each expected result quotes the real output. The harness refuses to run unless you pass --offline, so it never reaches a real service.

python emulation/runner.py --offline --all

A new source counts as supported only after it passes the same kind of scenarios. Each change also runs style checks, strict type checks, and the test suite on Python 3.12 and 3.13, and the suite must cover at least 90 percent of the code.

Privacy boundary

teamctx looks at shared work records. It does not watch people. The design rules out private chat, direct messages, email, editor activity, keystrokes, terminal history, agent prompts and replies, presence, productivity scores, and opinions about coworkers. The connectors built today read none of these.

  • Read-only. It writes nothing to your sources.
  • You turn on each repository, project, and docs folder.
  • Short facts first. No comments, patches, or bodies.
  • No broad search and no generated summaries.
  • Tokens stay in your environment or a file you name. teamctx never stores them.
