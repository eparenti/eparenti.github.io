How teamctx works

teamctx keeps you and your agent pinned to the current, source-backed state of the systems your team already uses. Its defining property is that there is no model in the content path: it normalizes, routes, selects, and renders the record, and never reinterprets what the record means.

The whole system

Approved sources are read by connectors into normalized artifacts. Safety and policy enforcement runs before anything is cached. A pure core derives relationships, evaluates the checks, and selects what to say. Three surfaces render the same answer.

What a check is

A check is one question about the work you are about to do, answered from a system of record. Each check returns exactly one of three verdicts, and every line carries the evidence it rests on.

Overlapping change
Another open pull request or merge request touches a file you are about to change. Your own same-repo pull request for the branch you stand on is set aside with an FYI; a fork pull request still surfaces.
Gate status
A check or pipeline on your branch is failing, or is still running, skipped, or canceled. Anything short of a completed success is reported as not yet confirmed green.
Acceptance criteria changed
The criteria on the linked GitHub or Jira issue changed after you started.
Doc superseded
A document under your declared docs folder names a newer replacement, or a Confluence page carries the teamctx.superseded_by property.
Source unavailable
A configured source could not be reached or could not be fully enumerated. This is its own finding, never folded into a clear.

Verdicts: clear, in the way, or not checked with the reason. A green means checked. Where teamctx could not look, it says so plainly instead of implying all is well.

Deriving the work context

teamctx derives the issue and the start time from what is already there: a Jira key like PROJ-123 or a GitHub issue number in the branch name, commit trailers, and the merge point with the base branch. The derivation is named in the output so you can judge it, and --issue names one explicitly when the branch does not.

teamctx work-start --path src/auth/token.py
teamctx why pr:7 --path src/auth/token.py
teamctx open-source pr:7 --path src/auth/token.py

Selectors are the handles you see in the output: pr:N, issue:#N, path:X, doc:PATH, gate:NAME.

Connectors and the policy gate

Connectors belong to source families with family-specific allowlists and default-deny fields. A new vendor must map into one of these families or add a reviewed family contract first.

FamilyExamplesDefault scopeExplicit exclusions
Forge reviewGitHub, GitLabOpted-in repos; pull request and merge request metadata; changed paths; check runs and pipelinesComments, patches, broad repository search
Work trackerGitHub issues, JiraOpted-in projects; issues, labels, structured acceptance criteria fieldsArbitrary comments, user analytics, query history
Docs and processLocal docs folder, ConfluenceLinked or allowlisted pages; supersession markers; timestampsWhole-space dumps, private docs, full bodies by default
Explicit chat handoffReserved in the architectureAllowlisted channels plus an explicit teamctx markerDirect messages, private channels, presence, reactions, broad history

Every artifact passes the policy gate before cache and before any finding is rendered. The gate applies field allowlists by family, blocks or redacts credential-shaped strings, reviews PII and confidentiality patterns, rejects unsafe URLs and paths, caps body and excerpt sizes, and classifies sensitivity. Unsafe artifacts are blocked, redacted, or quarantined; findings may report omission counts but never leak blocked content.

A permission filter rejects any artifact whose requester access cannot be proven. If permission proof is missing, the artifact is ineligible.

The purity boundary

The core package must be pure: no filesystem access, no network access, no subprocesses, no current-time reads, no randomness. It receives artifacts, relationships, policy configuration, and the clock as explicit inputs. All side effects live in connectors, the store, the CLI, or the servers.

This is why replay works. Feed the same inputs and the same verdict comes out every time, which is also what the emulation harness relies on.

Trust model

Source artifact text is untrusted data. Pull request titles and bodies, issue descriptions, comments, documentation text, and any third-party connector output must never become instructions for an agent or a developer tool.

message
Broker-authored deterministic text. The sentences you read.
source excerpt
Optional sanitized evidence, never instruction.
reason
The deterministic rule that caused the finding to appear.

Trusted inputs are the local policy configuration, the connector configuration, the deterministic rules, and the permission results from the source systems.

Three surfaces, one answer

The command line

teamctx work-start reproduces by hand what the hook shows, why prints the evidence for one finding, and open-source opens the record.

The Claude Code hook

Installed by teamctx onboard or teamctx install-hook. It grounds the session before its first edit, re-checks on an interval, speaks again when something changed, and re-states a standing gap every so often. It never blocks an edit.

Agents get the same answer over MCP. The CLI output, the MCP tool result, and the hook signal all derive from one broker answer and one shared classification, so the three can never disagree.

How the claims are proven

An offline emulation harness drives the real CLI, hook, and MCP tool through a 22-row scenario matrix against bundled mock GitHub, GitLab, Jira, and Confluence servers. Each expected block quotes the real renderer.

python emulation/runner.py --offline --all

A source becomes supported only after it proves the same honest-coverage behavior in the harness.

Privacy boundary

teamctx observes shared artifacts. It does not observe people. It must not collect private chat, direct messages, email, local editor activity, keystrokes, terminal history, agent prompts or responses, presence, productivity metrics, sentiment, or judgments about coworkers.

  • Read-only. It writes nothing to your source systems.
  • Explicit opt-in per repository, project, and docs folder.
  • Metadata first. No comments, no patches, no bodies by default.
  • No broad search and no generated summaries.
  • Audit logs record request shape and returned finding ids, never prompts, responses, or raw source bodies.
