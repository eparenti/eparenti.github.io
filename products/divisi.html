For people who run several coding agents on one machine

One container per context. No shared credentials.

Divisi runs AI coding agents in separate rootless Podman containers. Each context has its own home directory, credentials, git settings, and optional workspace mount. Host command guards help prevent accidental agent runs outside a context.

Keep work, open source, and experiments apart on one Linux machine: separate logins, separate git identities, separate files, and a guard that stops a bare agent command from running on the host.

Separate homes and logins

Sign in to GitHub and your agents separately inside each context. The home persists across container recreation and host reboots.

No overlapping mounts

A context mounts its own home and at most one host workspace. Shared and overlapping mounts are rejected, and divisi check verifies that the git email differs per context.

Host guards

When ~/.local/bin comes first on PATH, guarded command names refuse to run outside a context and log the tool name and time, without arguments.

Where Divisi sits on your host

What the separation is. Divisi reduces accidental account and file access across contexts. Each context sees only its own home and its one workspace mount. It does not isolate a hostile process from the host kernel, and containers use host networking, so they can reach host services.

From one shared home to three separate ones

The common failure is quiet: a work token used from a personal project, or an agent started in the wrong directory with the wrong git email. Divisi makes each context a separate place to stand.

Example: set up, sign in, check

Real commands
divisi init
divisi apply
divisi check

divisi enter work
gh auth login
exit

divisi run work git config user.email
divisi status

init writes ~/.config/divisi/divisi.conf and suggests three contexts. apply checks the host release, the subuid and subgid entries, and podman info before building.

Check passes: the contexts are separate

Every configured container runs, the path checks succeed, the git emails differ, and the guards are in place.

Check fails: fix the named prerequisite

A missing container, a failed path check, matching git emails, or a missing guard fails the check and names the problem. Run divisi apply again after fixing it.

Limits stated. Host guards can be bypassed by a direct path to another binary, a GUI app, or an IDE extension. Containers share the host network. Network controls are proposed in the egress plan and not implemented. A user can still add a second account inside a context.

Install on a supported host

Divisi targets RHEL 9, RHEL 10, and Fedora 40 or newer with a regular user account and rootless Podman. The first image build needs access to the Fedora registry and npm.

  1. Install Podman and git.

    sudo dnf install podman git, then confirm podman info works and that your user has entries in /etc/subuid and /etc/subgid.

  2. Put divisi first on PATH.

    Link bin/divisi into ~/.local/bin and put that directory first on PATH so the guards take priority over host agent CLIs. If another copy of a guarded CLI comes first, apply stops and reports it.

  3. Init, apply, check.

    Accept or rename the three suggested contexts. For a context without project files, leave the mount blank and choose no agent authentication, which is the default for experiments.

Install

git clone https://github.com/ostinato-forge/divisi.git
cd divisi
mkdir -p "$HOME/.local/bin"
ln -s "$PWD/bin/divisi" "$HOME/.local/bin/divisi"
export PATH="$HOME/.local/bin:$PATH"

First contexts

divisi init
divisi apply
divisi check

An Anthropic API key entered during init is written to that context's private ~/.secrets directory, never to the config file. CTX_SECRETS copies other named secret files the same way.

Commands
CommandAction
divisi initWrite an interactive local config
divisi applyBuild the image, recreate managed containers, install guards
divisi enter <name> / divisi run <name> <command>Open a shell, or run one command, in a context
divisi checkCheck container access, mounts, git email separation, and host guards
divisi auditScan host files and settings without changing them (needs ripgrep)
divisi enforce / relabel / statusRefresh guards, repair SELinux labels, show container state

Development checks: bash tests/test-core.sh, plus bash -n and ShellCheck over the scripts. The tests cover failed container checks, mount validation, API key handling, guard logs, and host release detection.

A focused first evaluation

Create the three suggested contexts, sign in to GitHub in two of them with different accounts, and run divisi check. Then try to start your agent CLI on the host and read what the guard says.
