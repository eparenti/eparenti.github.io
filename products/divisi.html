For people who run several AI coding agents on one Linux computer

Keep each AI agent's logins and files separate on one computer.

Divisi runs AI coding agents in separate containers (contained spaces on the same computer). Each context, such as work or open source, has its own home folder, logins, git identity, and at most one shared project folder. A guard on the host stops an agent command that is started outside a context.

The problem. People run several AI agents on one computer, for work, for open source, and for experiments. By default every agent can reach every login, key, and file on that computer, and one wrong command runs an agent with full access.

You get one command, divisi, that builds the contexts from a config file, checks that they stay separate, and puts the guards in place. It uses Podman (a tool that runs containers) in rootless mode, without administrator rights. The image includes the Claude Code, Codex, and Gemini command line tools.

Work logins stay in the work context

You sign in to GitHub and to your agents separately inside each context. Each context keeps its own home folder, so its logins survive a rebuild and a restart of the computer.

Each agent sees only its own files

A context mounts its own home and at most one project folder from the host. Divisi refuses shared or overlapping folders, and divisi check confirms that no context can see another context's folder.

A wrong command stops on the host

When you run claude, codex, or gemini outside a context, a guard refuses to run it and tells you how to enter a context. It logs the tool name and the time, without the command's arguments.

Where Divisi sits on your computer

What the separation covers. Divisi reduces accidental use of the wrong account or files across contexts. Containers share the host's kernel (the core of the operating system), so Divisi does not protect the host from a hostile program. Containers also use the host network, so they can reach services running on the host.

From one shared home to three separate ones

The common mistake is quiet: a work token used from a personal project, or an agent started in the wrong folder with the wrong git email. Divisi makes each context a separate place to work.

Example: set up, sign in, check

Real commands
divisi init
divisi apply
divisi check

divisi enter work
gh auth login
exit

divisi run work git config user.email
divisi status

init asks questions and writes ~/.config/divisi/divisi.conf, suggesting three contexts. apply builds the image and the containers. check confirms the contexts are separate. status shows whether each container is running.

The check passes: the contexts are separate

Every configured container runs, each one sees its own workspace and no other, the git emails differ, and the guards are in place.

The check fails: fix what it names

A missing container, a failed folder check, a git email used twice, or a missing guard fails the check, and the output names the problem. Fix it and run divisi apply again.

Limits. A guard covers only a command started by name. Starting another copy of the tool by its full path, a desktop app, or an editor extension skips it. To run a tool on the host on purpose, set DIVISI_OVERRIDE=1, and the guard logs that. Containers share the host network. Network controls are described in a design document and are not built. Nothing stops a person from adding a second account inside a context.

Install on a supported computer

Divisi runs on RHEL 9, RHEL 10, and Fedora 40 or newer, under a regular user account with rootless Podman. The first image build needs access to the Fedora image registry and to npm (the JavaScript package registry).

  1. Install Podman and git.

    Run sudo dnf install podman git, then confirm that podman info works and that your user has entries in /etc/subuid and /etc/subgid. Rootless Podman needs both.

  2. Put divisi first on PATH.

    Link bin/divisi into ~/.local/bin and put that folder first on PATH, so the guards come before the agent tools on the host. If another copy of a guarded tool comes first, apply stops and names the folder.

  3. Init, apply, check.

    Keep or rename the three suggested contexts. For a context with no project files, leave the folder blank and choose no agent sign-in. Those are the defaults for experiments.

Install

git clone https://github.com/ostinato-forge/divisi.git
cd divisi
mkdir -p "$HOME/.local/bin"
ln -s "$PWD/bin/divisi" "$HOME/.local/bin/divisi"
export PATH="$HOME/.local/bin:$PATH"

First contexts

divisi init
divisi apply
divisi check

If you enter an Anthropic API key during init, it is written to that context's private ~/.secrets folder and never to the config file. The CTX_SECRETS setting copies other named secret files into the same folder. Add the export PATH line to your shell startup file so it applies to new terminals.

Commands
CommandWhat it does
divisi initAsks questions and writes a local config
divisi applyBuilds the image, recreates the managed containers, and installs the guards
divisi enter <name> / divisi run <name> <command>Opens a shell, or runs one command, in a context
divisi checkChecks that containers run, workspaces stay separate, git emails differ, and guards are in place
divisi auditScans host files and settings without changing them (needs ripgrep)
divisi enforce / relabel / statusRefreshes the guards, repairs SELinux labels, and shows container state

Development checks are bash tests/test-core.sh, plus bash -n and ShellCheck (a checker for shell scripts) over the scripts. The operator guide lists ideas for later, such as small virtual machines for stronger separation and network controls per context. None of them is built.

A good first test

Create the three suggested contexts, sign in to GitHub in two of them with different accounts, and run divisi check. Then start your agent tool on the host by name and read what the guard says.
