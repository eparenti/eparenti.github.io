How Siglum works

Siglum decides whether the evidence from a pull request's checks is good enough to merge, and it leaves a signed record of that decision. This page explains the design in the order the gate applies it.

The whole system

Siglum uses two jobs, and the pull request can change only the first one.

A green check tells you that a check with the right name reported success. It does not tell you that the check ran on the exact code being merged, that it was not skipped, or that the pull request did not edit the check. Siglum splits the work into two GitHub Actions jobs (GitHub's built-in automation) and puts the trust boundary between them.

Every fact that matters to the result, such as which checks are required and at which version, comes from the rules on the base branch (the protected branch the pull request merges into). It never comes from the gather job's output. The trusted job never runs the author's code and never holds a key the pull request can reach.

Evidence becomes a result

The core takes the evidence about a change and computes one result. The same evidence always gives the same result, so anyone can recompute the decision offline later.

PASS
No required check failed or errored. PASS alone does not allow a merge: coverage must also be FULL.
FAIL
A required check reported a failure.
ERROR
A required check errored: it crashed, timed out, or could not finish cleanly.
Coverage
FULL when every required check gave a definite answer (passed or failed). A skipped, missing, or errored check makes coverage INCOMPLETE. A skipped check is never a pass.
Independence
Met when the run's verified identity matches the gate identity your organization pinned in its rules. When the rules do not require it, as in the dry-run tier, it is marked as not required.
Decision hash
A fingerprint over the evidence and the result. Siglum recomputes it whenever a stored or posted result is read back, and rejects any result that does not match. It leaves out timestamps and run ids.

A change may merge only when the result is PASS, coverage is FULL, and independence is met or not required. Anything missing blocks the merge. This is called failing closed.

The order of checks

The trusted job makes these checks in order. The order is part of the design. Each check fails closed and posts a failing result before the next one runs.

  1. Identity. In the Sealed tier the gate asks GitHub for its own OIDC token (a short-lived, signed identity token that GitHub gives each workflow run). It verifies the token's signature, issuer, audience, and expiry. Then it checks the token against the gate identity your organization pinned: the repository, the workflow, a protected branch or tag the author cannot edit, and a GitHub-hosted runner. The name of the person who started the run never counts as proof. Tests cover forged and malformed tokens: unsigned tokens (alg:none), the wrong key type, the wrong issuer or audience, expired tokens, bad signatures, self-hosted runners, and missing runs.
  2. Strict identity rules. The gate identity rules are read from the base branch and parsed strictly. A wildcard workflow path is rejected, and a concrete workflow path and at least one branch or tag are required. siglum setup check confirms that the named branch is the protected default branch.
  3. Settings self-check. The gate reads its own settings through the GitHub App. It fails closed unless the siglum check is required on a protected branch and accepted only from the Siglum App. Rules that require independence but have no App credentials also fail closed.
  4. Evidence clean-up. Whether each check is required, and its pinned version, come from the base branch rules. A required check that the gather job did not report becomes UNKNOWN, which fails closed. Duplicate check ids are rejected, and ids the base rules do not name are ignored.
  5. Protected inputs. The trusted job reads the pull request's version of each protected file itself, at the pull request's commit, through the GitHub App. It fails closed if the pull request changed one of them, such as the rules file, a scanner setting, or a workflow.
  6. Approval tied to the commit. This check is optional (approval_required in the rules). The gate reads the reviews with its own token and works out which commit each reviewer approved. A later request for changes clears an approval. The approved commit must equal the commit being checked, so approving one commit and then force-pushing another fails closed, and the comment asks for a new approval. In a merge queue (a GitHub feature that merges approved pull requests one at a time) the gate instead confirms that the default branch requires an approving review.
  7. Recompute, then sign. The result and the decision hash are recomputed whenever they are read back. In the Sealed tier the gate signs the result and verifies the signature before it posts success. A green check always has a verified, signed record behind it.

The signed record

The result is sealed into an in-toto attestation (a standard format for signed statements about software). It does for validation what SLSA build provenance does for builds; SLSA is a public framework for software supply-chain security. Signing goes through Sigstore without a long-lived key: Sigstore issues a short-lived certificate tied to the workflow's identity and records the signature in a transparency log (a public, append-only log). You verify the record offline with cosign, with no Siglum service involved.

cosign verify-attestation \
  --type https://siglum.dev/ValidationAttestation/v0.3 \
  --certificate-identity-regexp '^https://github.com/your-org/' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  your-artifact

The two certificate flags are the identity rule: only a signature made by a GitHub Actions workflow in your organization passes.

The record covers the commit that is about to merge. A release of a different artifact is outside that claim unless your release workflow checks the record for the exact commit it releases. That optional step is the release gate.

Signing is pinned to Sigstore's test service (staging) and refuses the production service until that path is reviewed. Until production signing is in place, treat every signed record as a test record.

Two tiers, one core

Siglum runs in two ways. Both use the same result calculation.

Dry-run

Runs in your normal CI and previews the result.

Use it to write your rules and to find checks that skip without failing.

It does not confirm its identity and does not sign.

Sealed

Runs in a workflow your organization controls, outside the pull request's own workflows.

Confirms its own GitHub identity and signs the result.

Protects against a contributor who can push and edit CI but has no organization admin rights.

A pull request from an AI agent is treated the same as one from any other contributor. The guarantee never depends on trusting the author, so it holds whether the author is a person or an agent.

What Siglum does not protect against

The design has these limits and rests on these assumptions.

  • A compromised organization administrator. An administrator who turns off branch protection, removes the required check, or changes the pinned workflow defeats the gate. The self-check finds a missing or loose setup. It cannot stop an administrator who turns enforcement off.
  • Checks that run the author's code. The design is sound for read-only checks, which apply the base branch's logic to the pull request's files. That is why this version ships only one check: a read-only scan for leaked secrets.
  • Whether the checks are good enough. Siglum attests that the checks ran and that the result follows from their evidence. It does not judge whether they were the right checks or strict enough.
  • Production signing. Records signed on the test service are not production evidence.

The guarantee also assumes three things. GitHub's identity tokens, branch protection, and rulesets work as documented. Your organization deploys the pinned workflow and accepts the siglum check only from the App. The App's credentials are stored as organization or repository secrets that the pull request cannot reach.

What is tested

The decision logic is covered by unit tests that use simulated GitHub and Sigstore calls. Every live call the gate makes, such as signing or reading GitHub settings, runs only in a real workflow run.

Using it

Try Siglum locally first, then deploy the gate.

git clone https://github.com/siglum-dev/siglum && cd siglum
python -m pip install -e ".[dev]"

# where can the merge check be bypassed today? reads only, changes nothing
siglum audit --repo owner/name

# walk the whole flow locally with no GitHub access
siglum demo scaffold --out /tmp/gate-proof-demo --repo owner/gate-proof-demo --force
cd /tmp/gate-proof-demo
siglum audit --config siglum-audit-config.json || true
siglum setup check --local .

The demo audit finds one gap on purpose and exits 1. The || true keeps the walk-through going to the setup check, which shows what a ready Sealed install looks like.

To deploy the Sealed gate, register a GitHub App in your own organization. Add the gather and seal-and-enforce workflows, pinned to a version contributors cannot edit. Make the siglum check required in your ruleset and accept it only from that App. Store the App id, installation id, and private key as the secrets SIGLUM_GITHUB_APP_ID, SIGLUM_GITHUB_APP_INSTALLATION_ID, and SIGLUM_GITHUB_APP_PRIVATE_KEY. Set the SIGLUM_PACKAGE_SPEC repository variable to a commit or a pinned release, so the code the trusted job installs stays fixed.

Siglum gates merges. A release workflow that runs from a tag or a branch can ship code that never passed the gate. To cover what you ship, the release job must verify the signed record for the exact commit and stop without one. siglum release-check performs that check.
