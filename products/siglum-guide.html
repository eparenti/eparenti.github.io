How Siglum works

Siglum sits on top of the validators you already run and decides whether their evidence is trustworthy enough to merge, then leaves a signed record of that decision. This page explains the design, in the order the gate enforces it.

The whole system

A green check tells you that a check with the right name reported success. It does not tell you the check ran on the exact code being merged, that it was not silently skipped, or that the pull request did not edit the check on its way in. Siglum splits the work across two jobs and puts the trust boundary between them.

Every security-relevant fact about the verdict, which validators are required and at which pinned version, is taken from the base policy and never from the gather artifact. The trusted job never runs the author's code and never holds a token the pull request can reach.

Evidence becomes a verdict

The core takes the evidence about a change and computes one verdict. It is a pure function: the same evidence always produces the same verdict, and a verifier can re-run the decision offline later.

PASS
Every required validator ran to completion and reported success.
FAIL
A required validator reported failure.
ERROR
The evidence is malformed, a policy could not be read, or a validator ended in a state the policy cannot accept.
Coverage
FULL when every required validator produced evidence; INCOMPLETE otherwise. A skipped validator is a coverage gap, never a pass.
Independence
Satisfied when the gate's identity, the enforcement configuration, and the anchored inputs all held during the run.
Decision hash
A digest over the evidence and the verdict. Anything stored or posted is recomputed on deserialization and rejected if it does not recompute.

A change is mergeable only when the verdict is PASS, coverage is FULL, and independence is satisfied. Anything missing fails closed.

The order of enforcement

The trusted gate enforces these stops in order, because the order is part of the design. Each stop fails closed and posts a failing check before the next one runs.

  1. Identity. At the Sealed tier the gate mints its own GitHub Actions OIDC token, verifies its signature, issuer, audience, and expiry, and enforces the claims against an org-pinned gate-identity policy: the repository, the workflow reference, a protected ref the author cannot edit, and a hosted runner. The trigger actor string is never the authority. The conformance suite rejects alg:none, key-type confusion, a wrong issuer or audience, expiry, a bad signature, a self-hosted runner, and an absent run.
  2. Policy tightness. The gate-identity policy is anchored to the base and parsed tight: a wildcard workflow path is rejected, and a concrete workflow path and a non-empty list of refs are required. siglum setup check verifies that the declared ref is the protected default branch.
  3. Enforcement self-audit. The gate reads its own enforcement configuration through the App API and fails closed unless the siglum check is required on a protected branch and source-restricted to the Siglum App by id. A policy that requires independence but has no App credentials also fails closed.
  4. Evidence normalization. The required flag and the pinned version for every validator come from the base policy. A base-required validator the gather job did not produce is filled with UNKNOWN, duplicate ids are rejected, and ids the base policy did not declare are ignored.
  5. Anchored inputs. The trusted job reads the head version of each anchored path itself, at the head SHA, through the App contents API, and fails closed when the head overrides a base-anchored input such as the policy, a scanner config, or the workflow.
  6. Approval binding. When the policy requires approval, the approved SHA is computed per reviewer from the reviews the gate reads with its own token, cleared by a later request for changes, and must equal the head being gated. Approve one commit and force-push another fails closed, and the comment asks for a re-approval of the current head. In a merge queue the gate proves instead that the protected target branch requires an approving review.
  7. Recompute guard, then signing. The verdict and the decision hash are recomputed on deserialization. At the Sealed tier the gate signs the attestation and self-verifies the signed bundle before it posts success. There is never a green check without a verified attestation behind it.

What the attestation contains

The verdict is sealed into an in-toto validation predicate, the validation-side sibling to SLSA build provenance. It is keyless-signed through Sigstore, recorded in a transparency log, and verifiable offline with cosign and a strict identity policy, with no Siglum service in the loop.

cosign verify-attestation \
  --type https://siglum.dev/ValidationAttestation/v0.3 \
  --certificate-identity-regexp '^https://github.com/your-org/' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  your-artifact

The attestation's subject is the merge candidate. A release of a different artifact is outside the claim unless the release workflow checks the attestation for the exact commit being released, which is the opt-in publish gate.

Signing is pinned to Sigstore staging and refuses to run against production, because production signing is deliberately gated behind explicit review. Until that path is wired, every attestation should be treated as non-production.

Two tiers, one core

Dry-run

Runs in your normal CI and previews the verdict.

Use it to author policy and to see where a gate silently skips.

No verified identity. It does not sign.

Sealed

Runs in an org-controlled workflow outside the pull request's pipeline.

Verifies its own GitHub Actions OIDC identity and signs the attestation.

Defends against a contributor who can push and edit CI but has no organization-admin rights.

A pull request from an AI agent is treated exactly like one from any other contributor. The guarantee never depends on trusting the author, so it holds whether the author is a person or an agent.

What Siglum does not defend against

  • A compromised organization administrator. An admin who disables branch protection, removes the required check, or changes the org-pinned workflow defeats the gate. The runtime self-audit detects a missing or loose deployment; it cannot stop an administrator who turns enforcement off.
  • Validators that execute head-authored code. The model is sound for read-only validators, which apply base logic over head data. That is why this version ships only the read-only secret-scan validator.
  • The adequacy of the validation. Siglum attests that the validators ran and that the verdict follows from their evidence. It does not judge whether they were the right validators or strict enough.
  • Production-grade signing. Staging attestations are not production evidence.

The guarantee also rests on stated assumptions: GitHub's OIDC issuer, branch protection, and rulesets behave as documented; the organization deploys the pinned workflow and restricts the siglum check to the App; and the App's credentials are held as organization or repository secrets the pull request cannot reach.

Status discipline

The decision logic is unit-tested through in-memory fakes. Every live call the gate makes at runtime is exercised only in a real CI workflow, never in unit tests. The split is stated for each part.

Using it

git clone https://github.com/siglum-dev/siglum && cd siglum
python -m pip install -e ".[dev]"

# where can the gate be bypassed today? reads only, changes nothing
siglum audit --repo owner/name

# walk the whole flow locally with no GitHub access
siglum demo scaffold --out /tmp/gate-proof-demo --repo owner/gate-proof-demo --force
cd /tmp/gate-proof-demo
siglum audit --config siglum-audit-config.json || true
siglum setup check --local .

To deploy the Sealed gate: register a GitHub App in your own organization, deploy the org-controlled seal and enforce reusable workflow pinned to an immutable ref, make the siglum check required in your ruleset with its source restricted to that App, and give the workflow the App id, installation id, and private key as secrets. Point SIGLUM_PACKAGE_SPEC at a commit SHA or a pinned release so the code the trusted job runs cannot drift.

Siglum is a merge gate. A release workflow that runs off a tag or a branch can ship an artifact whose source never passed the gate. To extend the claim to what shipped, the release job must verify the attestation for the exact commit and fail closed without one.
